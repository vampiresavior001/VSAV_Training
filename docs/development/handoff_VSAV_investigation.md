## 2. 系統5：透明化バグ（解決済み）

### 症状

シャドウブレイドのリバーサルで、キャラクターが透明になる。やられ判定も消えるため無敵状態になる。左右入れ替えを伴う場面で起きやすいと報告されていたが、後述の通りこれは直接の原因ではなかった。

### 原因

`0xFF890C`（P2ベース、既存の系統4で扱う5バイトのうち`0xFF890D`の**1バイト前**）が原因だった。

このバイトは、被弾中・ダウン中は数フレームおきに `0x00` ⇔ `0xFF` を繰り返す。通常の被弾フラッシュ／点滅表現とみられる。系統4の5バイトと違い、「残っていると悪さをする残骸」ではなく、**リバーサルのpoke（技の強制開始）が、この点滅を止めずに放置してしまう**のが問題だった。

- ポークの瞬間にたまたま点滅が `0xFF` 側で止まっていた場合 → その値のまま以後 約65〜67フレーム（リバーサル中ずっと）固定 → **透明化**
- `0x00` 側で止まっていた場合 → 固定されても見た目は正常

つまりタイミング次第で結果が変わる**レースコンディション**であり、これが「起きたり起きなかったり」する理由。左右入れ替えは、やられ硬直が長引く場面で起きやすいために間接的に相関して見えていただけで、直接の引き金ではない。

### 修正

`guardCancel.lua` の `poke_special()` に、既存の5バイトクリアと同じ場所・同じ書式で1行追加。

```lua
memory.writebyte(0xFF890C, 0x00)
```

ポークの瞬間に強制的に「表示」側（`0x00`）へ固定する。実機で10〜20回の連続テストで再現せず、確定。

### 副産物：マーク機能の追加（`debugKnockdown.lua`）

調査中、計測ビルドの `debugKnockdown.lua` に以下を追加した（**計測専用、通常動作には影響なし**）。

- **Lua Hotkey 2** を押すと、直前の記録に「見た瞬間のフレーム」を残せる（`marks` 配列）
- マーク付きの記録は `reversal_logs/kd_m01.json`〜`kd_m08.json` という別リングに保存され、通常の `kd_s01〜12` に上書きされない
- ポークが無い（システムからのリバーサル書き込みが起きなかった）記録は保存されなくなり、無関係な被弾でリングが埋まらないようにした
- `session` / `seq` フィールドで新しい記録を一意に識別できる

透明化を見た瞬間にHotkey 2を押すことで、「どのログが問題の回か」を推測せず確定できるようになった。**今後も同種の調査で有効なので残しておく。**

### 調査で分かった副次的な知見

- 受付カウンタ `0xFF8974` が `5`（ガード硬直・やられ硬直からのリバーサル）の場合のみ透明化が起きうる。`9`（起き上がりリバーサル）では一度も発生していない。ただし `5` だけでは不十分で、単独では透明化を予測できない
- `0xFF8944`（同一ダウン中の連続リバーサルで1→2→3→4→5と増えるカウンタ）が毎回別ダウンにもかかわらず1のまま持ち越されている現象を発見。これ自体は透明化の原因ではなかったが、別途「本来リセットされるべきタイミングでリセットされていない」バグとして記録しておく（下記「失敗した対処」参照）
- 左右入れ替え（`fa2`反転）は、透明化した回・しなかった回の**両方で同じタイミング**（poke後38〜39F、67〜68F）に起きており、単独の原因ではなかった

## 3. 系統6：ES/EXのパレット効果が出ない（解決済み）

### 症状

ES版シャドウブレイドが本来の青白い発色にならない。ダークネスイリュージョン等、キャラ固有のEX専用技も演出が出ない。**系統5（透明化バグ）の修正とは無関係と実機A/Bテストで確認済み**（`0xFF890C`のクリアを外しても青くならないままだった＝修正前から存在した別問題）。

### 原因

`poke_special()` に元々あったパレット効果コードが2つとも死んでいた。

```lua
-- whenever strength is es or ex then specify pallete effect
-- 0x14E 	Palette Effects & Curse , ES/EX, etc
-- ES Value is 1E
-- EX Value is 1C
-- if move_strength == 0x06 then
-- 	memory.writebyte(0xFF8800 + 0x14E , 0x1E)
-- end
-- if isEX then
-- 	memory.writebyte(0xFF8800 + 0x14E , 0x1C)
-- elseif move_strength == 0x06 then
-- 	memory.writebyte(0xFF8800 + 0x14E , 0x1E)
-- end
```

- 両方ともコメントアウトされたまま放置されていた
- `isEX` はこの関数どころかファイル内のどこにも定義されていない変数（未定義グローバル＝常に`nil`）で、有効化しても発火しない
- **`0x14E`に書く値がES/EXで逆**：コメントは「ES=1E, EX=1C」としていたが、実機確認では **`0x1E`＝点滅（EXの見た目）、`0x1C`＝青白い発光（ESの見た目）** だった

### 修正

`guardCancel.lua` に2つ変更を加えた。

1. `move_is_ex(move_value)` を新規追加。`globals.char_moves.P2.all`（`charMovesModule`が毎フレーム再構築、`vsav_training_master_script.lua`内で`guardCancel`より先に実行される）から`move_value`に一致する技を探し、`charMoves.lua`で個別に付与されている`isEX`フィールド（例：モリガンのダークネスイリュージョン）を見る
2. `poke_special()` 内、死んでいた2つのブロックを1つの正しい分岐に置き換え

```lua
if move_is_ex(move_value) then
	memory.writebyte(0xFF8800 + 0x14E, 0x1E)  -- EX専用技: 点滅
elseif move_strength == 0x06 then
	memory.writebyte(0xFF8800 + 0x14E, 0x1C)  -- Strength=ES: 青白い発光
end
```

技自体がEX専用（`isEX=true`）かどうかを優先し、そうでなければStrengthドロップダウンのES選択を見る。実機でES版シャドウブレイド、EX専用技の両方を確認済み。

`0xFF894E`（`0x14E`と同じ）は`vsavscriptv2.lua`のHUD表示（呪い状態"CURSED"の判定、ワード値`0x0808`）でも参照されているが、書き込み値`0x1E`/`0x1C`とは一致しないため衝突しない。

### 追加修正：起き上がりリバーサルでESが発色しない

上記の修正だけでは不十分だった。実機で確認すると、**起き上がりリバーサル（受付カウンタ`0xFF8974`が`9`）ではES/EX演出がほぼ毎回1フレーム後に消える**（`0xFF894E`が`0x1C`/`0x1E`書き込みの1フレーム後に`0x00`へ戻る）。ガード硬直・やられ硬直からのリバーサル（`rev=5`）では問題なかった。何が戻しているかは未特定だが、`retry_if_swallowed()`と同じ「1フレーム後に検証・再書き込み」の考え方で対策した。

`poke_special()`で書き込んだ直後に`pending_palette = { value = ..., frames_left = 5 }`をセットし、`guardCancelCheck()`の先頭で毎フレーム呼ばれる新しい`reassert_palette_effect()`が5フレームの間書き直し続ける。`rev=5`の場合は同じ値を無害に書き直すだけなので副作用はない。実機でrev=9のES/EX両方を確認済み。

## 4. 系統7：コンボ/ヒット数の引き継ぎバグ（解決済み）

### 症状

P2がリバーサル必殺技を出し、ニュートラルを取る前に（デミトリ等の）攻撃を受け、再度リバーサル…を繰り返すと、画面のHITカウンターが本来なら各リバーサルごとにリセットされるべきところ、蓄積し続ける（実測で5、8まで確認）。

### 原因

`0xFF8944`（`b144`。系統4の「クリアしないバイト」として既に知られていたもの。「同一ダウン中に連続でリバーサルを出すと1→2→3→4→5と増えるカウンタ」と説明されていた）が、**画面のHITカウンターと連動していた**。連続テストで受けたヒットのたびに1ずつ増える様子（`1,2,4,1,2,3,5,6,7,8`、最後の値が実際の画面表示と一致）をログから確認した。

このバイトは以前、潰れバグ調査の際に「poke時にクリアするとシャドウブレイドのアニメが消える」と分かっており、系統5の透明化バグ調査でも同様の懸念から`arm_edge`限定のクリアを試して効果なしと判断し見送っていた（`guardCancel.lua`内のコメント参照）。

### 修正

依頼者の指示により、リスクを承知の上で`poke_special()`内、リバーサル書き込みの一部として`memory.writebyte(0xFF8944, 0x00)`を追加（毎回・無条件）。

実機で **HITカウンターのリセットとシャドウブレイドのアニメ、両方とも問題なし** と確認済み。以前「アニメが消える」と分かった状況との違いは不明（潰れバグ調査時とは異なる状況・異なる値域だった可能性がある）。**もしシャドウブレイドのアニメが消える報告が今後あれば、真っ先にこの1行を疑って戻すこと。**

### 調査中に外れた候補（記録）

- **P1+0x1B7 / P1+0x1B9**：最初のテスト（5回のヒットイベント）で`2,3,4,5,7`と綺麗に増えていたため有力候補と判断したが、実機でクリアしても効果なし。サンプル数が少ないまま確信を持ちすぎた失敗例。**サンプルが少ないうちの「綺麗な増加パターン」は過信しないこと**

## 5. 系統8：潰れバグ（解決済み）

### 症状

リバーサルのシャドウブレイドに、デミトリのジャンプ攻撃を重ねると潰される。安全飛び込みのセットプレイで再現。**ターボだけでなく通常速度でも発生する**ため、tick単位のタイミングのずれが原因ではない。

### これまでの手がかり（原因の一部）

受付カウンタ `0xFF8974` の初期値で結果の傾向が分かれていた。

| 受付カウンタ | 残骸あり | 件数 |
|---|---|---|
| `9` | 0 / 13 | 全て正常 |
| `5` | 25 / 28 | ほぼ全て残骸あり |

`9` は起き上がりリバーサル、`5` はガード硬直・やられ硬直からのリバーサルと推定。潰れバグは後者でのみ発生。

`0xFF8944` をクリアすれば潰れは直るが、シャドウブレイドのアニメが消えるという記録が残っていた（実機確認済み、2通りの場所で試して両方とも同じ結果）。ただし系統7で同じ場所に同じクリアを既に入れており、それでも潰れバグ自体は直っていなかった（実機で再確認済み）。つまり `0xFF8944` は潰れバグの直接の原因ではなかった。

### 本当の原因

マーク付きログ（`kd_mNN.json`）で、同じ記録内にあった「潰れた回」と「潰れなかった回」の2つのpokeを直接比較して判明。

- **潰れなかった回**：poke の**1フレーム後**に無敵タイマー `0xFF8947` が `0` から `10` に変わり、無敵が機能する
- **潰れた回**：poke の1フレーム後に再び被弾しており、`0xFF8947` は記録の最後まで一度も `0` から動かない

つまり、ゲーム側が実際に無敵タイマーをセットするのは **poke の1フレーム後**（新しいアクションバイトを処理した結果として）であり、そのpokeした瞬間そのものにはまだ無敵になっていない。重ね技の判定がその1フレームの隙間に間に合ってしまうと、無敵が発動する前に被弾し、リバーサルが潰される。

### 修正

`guardCancel.lua` の `poke_special()` に1行追加、poke と同じフレームで無敵タイマーを立てる。

```lua
memory.writebyte(0xFF8947, 0x01)
```

ゲーム自身がpokeの次のフレームで正しい無敵時間（技ごとの本来の値）を上書きするため、ここで書く値は「その1フレームだけ無敵と判定されればよい」プレースホルダーで構わない。`0xFF8947` は `cps2-hitboxes.lua` と `timers.lua` で読み取り専用参照されているのみ（`> 0`判定のみ）で、他に書き込んでいる箇所はない。

実機で安全飛び込みのセットプレイを約50回試し、**潰れ0件**と確認済み。

## 6. 新機能：アナカリス「咎めの穴」対応（`guardCancel.lua` / `charMoves.lua`）

### 背景

「咎めの穴」（Pit of Blame）はリバーサル技ではなく、**自分のダウン中に、相手の追い打ちを吸い込むために出す**特殊な技。既存のリバーサル受付窓は起き上がり付近でしか開かないため、メニューから選べても実際には出せなかった。

### 修正1：技IDの誤り（`charMoves.lua`、確定・変更なし）

アナカリスの技テーブルに「Pit of Blame」が**2つ**登録されており、片方が誤って `0x1C` になっていた。

- `0x16` = Pit of Blame（正）
- `0x1C` = Pharaoh Decoration（別の技。当時の一覧と本書は P. Salvation と書いていたが、2026-10-07 に 0x14 = Salvation、0x1C = Decoration と直した。`charMoves.lua` の get_moves_Anakaris の注記）

名前で技を引く仕組み（`dummyState.lua` の `get_p2_char_specific_reversal`）は**最後に一致したものを採用**するため、「Pit of Blame」を選ぶと実際には `0x1C`（Pharaoh Decoration）が叩かれていた。誤った重複エントリを削除。

### 修正2：発動方式 — メモリpokeから実コマンド入力へ

**旧方式（当初の実装）**：`0xFF8980` が `0`→`1` になってから固定フレーム待って `run_one_frame_special()`（＝メモリpokeで技IDとアクションバイトを直接書き込む）を呼んでいた。動作はしたが、**pokeはゲームが技開始時に本来行う処理を素通りするため不整合が出る**という報告があり（`action_slot` ガード迂回によるフリーズリスクも含む）、実際のコントローラー入力（DPF＋キック）を `queue_input_sequence()` で送り、技が出るかどうかはゲーム自身の判定に委ねる方式に切り替えた。

これに伴い：
- `poke_special()` の `action_slot` 迂回（旧・修正3）は不要になり**削除した**。実入力はゲーム自身の受理判定を通るため、pokeのための迂回そのものが要らない
- サイド入れ替え（キャラの左右反転）も `queue_input_sequence` 側の既存の向き追従機構でそのまま処理される。pokeでは素通りしていた部分

### 発動タイミングの再調査（今回の主眼）

実コマンド化した直後、**P2側の入力履歴にはDPF+Kのコマンドが正しく表示されるのに、技そのものが出ない**という症状が発生した。以下、試行錯誤の全履歴（すべて実機確認）。

1. **`0xFF8980` の立ち上がりで即座に送信（保持なし）** → 履歴には正しく出るが技が出ない
2. **同じ `0xFF8980` の立ち上がりで方向だけ保持し、11フレーム後にボタンだけ離す（`hold_last`＋`release_input_sequence`）** → さらに悪化。履歴に方向すら出なくなった
3. **P1側実測（ヒット発生を起点に、Y座標も含めて記録し直し。従来の計測は `0xFF8980` のエッジからしか記録しておらず、それより前の入力を見落としていた）** で判明した事実：
   - `0xFF8980` は、**Y座標が実際に地面の高さへ戻ってから 20〜24 フレームも後**に立ち上がる。「着地」ではなく、もっと後の合図（起き上がり許可等）だった
   - 人間の実際のボタン入力（7サンプル全て）は、ヒットから **+40〜48フレーム**、すなわち**実測着地（+45〜50F）の直前〜直後**に集中していた。`0xFF8980`（+70〜71F）より20フレーム以上前
   - 上記2.の「11フレーム後に離す」は `0xFF8980` 基準で+11F、つまり実際の着地から見ると **+31〜35F**も遅れていた。しかも約69フレームもの間ホールドしていたため、`service_held_reversal()` の別のプリバッファ機構にある「入力は約10フレームしか生存しない」という既知の制約（`HOLD_LIMIT`）にも抵触していたと考えられる
4. **怯み/ガード硬直開始（`status_1==0x02`）から固定28フレーム後に送信** → 単発のダウン技では正しく発動した（このタイミング自体は正しかった）。ただし2つの問題が残った：
   - **ダウンしない通常のヒット/ガードでも `status_1==0x02` にはなるため誤発動**した
   - **しゃがみ小・中・大キックのようなチェーンコンボ**では、`status_1==0x02` がコンボ全体を通じて連続して真のままなので、**最初のヒットから28F**で送信してしまい、肝心のダウン技（コンボ終盤）のヒットに間に合わなかった
5. **`globals.dummy.p2_in_air`（0xFF8800+0x38）の 0→非0→0 で「空中に浮いて着地した」を検知** → 全く発動しなくなった。このフラグはおそらく任意ジャンプの状態機械専用で、ダウンの吹っ飛びでは変化しないと推測される（未確認）
6. **Y座標（`globals.dummy.p2_y`、`0xFF8800+0x14`）で「怯み開始時基準+15浮いたら空中」「その後、基準+5以内に戻ったら着地」を検知** → これも発動せず

### 現在の実装（確定）

**Y座標で「空中に浮いた」ことを検知した瞬間を起点に、固定 `PIT_OF_BLAME_INPUT_DELAY` フレーム後に無条件で送信する**（着地を待たない）。

```lua
local PIT_OF_BLAME_INPUT_DELAY  = 22   -- 実機調整により 28 → 22
local PIT_OF_BLAME_AIR_MARGIN   = 15   -- 怯み開始時のYからこれ以上浮いたら「空中」
```

- 起点は「怯み/ガード硬直開始」ではなく「**その怯み区間内で最初に空中判定が出た瞬間**」。単発ヒットでは怯み開始とほぼ同時（数フレーム差）なので4.で確認済みの良好なタイミングをほぼ引き継ぐが、**チェーンコンボでは実際にダウンさせたヒットの瞬間を正しく捉える**（Y座標は通常のチェーン打撃では動かないため、ダウン技のヒットで初めて空中判定が立つ）
- 通常のヒット/ガードはYが動かないため、そもそもこのカウントが始まらない → 誤発動しない
- **多段の空中コンボ対応**：カウント中に `0xFF8944`（系統7で確認済みのヒットカウンタ、コンボ中1発ごとに増加）の値が変化したら「新たなヒットがあった」とみなし、その瞬間からカウントを再スタートする。これにより空中で複数回ヒットするコンボでも、**最後のヒットから `PIT_OF_BLAME_INPUT_DELAY` フレーム後**に送信される
- `PIT_OF_BLAME_INPUT_DELAY` は当初28で単発ダウン技は動作したが、**実機で「なかなか出ないケースあり」との報告を受けて22に調整**した実測値。理論上の根拠（P1計測の着地タイミング）とは別に、実際のコマンド受理タイミングに合わせて微調整されたものなので、今後さらに調整が必要になる可能性がある

**未検証・注意点**：`0xFF8944` が空中ヒットでも地上のチェーンヒットと同様に増加するかは、地上のリバーサル→めくり連続ヒットでしか実機確認していない。もし多段空中コンボでタイミングがずれる場合はまずここを疑うこと。

### 修正3.5：ターボ3で出ない（実機確認済み）

**症状**：ターボ3では咎めの穴が出ない。「受付時間が延びる」ケースでは稀に出る、との報告。

**原因**：`PIT_OF_BLAME_INPUT_DELAY` のカウントは、`service_held_reversal()` の呼び出し1回につき`+1`していた。これは**表示フレーム単位**のカウントだが、ターボ3は「表示3フレームでゲームの内部tick 4回分」進む（`0xFF8081` が `1,1,2,1,1,2...` と進む。系統4のリトライ機構で既に文書化されていた挙動）。つまりターボ3では、カウントが22に達するまでの間にダブルティックフレームが挟まった分だけ、**実際のゲームtickでは22より多く経過してしまう**（22 × 4/3 ≒ 29tick）。通常速度で調整した値がターボ3では約7tick遅れて送信されることになり、受付時間が実測（6章参照）とずれて技が出なかった。「稀に出る」のは、ダブルティックが偶然少なめに挟まった回でずれが小さく収まったため。

**修正**：`+1` の代わりに、その呼び出し間の `0xFF8081` の差分を加算するようにした。バイトカウンタなので255→0の折り返しも `% 256` で処理している。これで表示フレーム数ではなく実tick数でカウントするようになり、速度設定に関係なく `PIT_OF_BLAME_INPUT_DELAY` が同じ実時間を意味するようになる。

```lua
local _tick = memory.readbyte(0xFF8081)
pit_of_blame_frames = pit_of_blame_frames + ((_tick - pit_of_blame_prev_tick) % 256)
pit_of_blame_prev_tick = _tick
```

### 修正3.6：`Character Specific Counter` 経由でまだpokeされていた（実機確認済み）

**症状**：「咎めの穴はメモリ書き換えで出さない」という決定事項に反し、実際にはpokeで出るケースが残っていた。

**原因**：`run_one_frame_special()`（pokeで技を出す関数）を呼ぶ箇所は `guardCancelCheck()` に2つある。`guard_action == 'Character Specific Reversal'` 側だけ `move_is_pit_of_blame()` で除外していたが、`guard_action == 'Character Specific Counter'` 側には**除外がなかった**。CSRのドロップダウンで選ぶ技リストは両モードで共有されているため、Counterモードで咎めの穴を選ぶと、実入力化の対象外である旧pokeパスをそのまま通っていた。

**修正**：呼び出し側ごとに除外を書く方式は今後another似た抜けが起きうるため、`run_one_frame_special()` 自体の入口（nilガードの直後）に `if move_is_pit_of_blame() then return end` を追加した。これで呼び出し経路に関係なく、咎めの穴が絶対にpokeされないことを関数側で保証する。

### 修正4：通常のリバーサル経路から除外（変更なし）

通常のリバーサル窓はダウンしない普通のヒットやガードでも開くため、この技を通常経路にも残すと**ダウンしない技で誤発動**した。除外した。

### 修正5：Guard Action Frequency（出現率）が効かない（変更なし）

独自トリガーにした結果、**頻度設定を無視して毎回出る**ようになっていた。`guardCancelCheck()` 内の `shouldGC()` は早期returnの後ろにあり、独自トリガーはその手前で動くため、そもそも抽選対象外だった。

**抽選はダウン1回につき1回だけ**、怯み/ガード硬直の開始（武装した瞬間）で行い、結果を保持して発動フレームで参照する。毎フレーム走る場所で抽選すると実質100%になるため（先読み入力の実装にも同じ注意書きがある）。実機で確認済み。

### 併せて修正：キャラ変更時のクラッシュ（元からある潜在バグ、変更なし）

`run_one_frame_special()` は `globals.dummy.p2_char_specific_reversal.value` をnilチェックなしで参照していた。技選択インデックス `p2_reversal_list` は**キャラ変更時にリセットされない**ため、アナカリス（14技）で12番目を選んだままモリガンに変えると、その番号の技が存在せず nil になりクラッシュする。

```
guardCancel.lua:278: attempt to index field 'p2_char_specific_reversal' (a nil value)
```

nil なら何もせず `return` する1行を追加。**この技を追加したことによる不具合ではなく、元からあったもの**（キャラを切り替えて初めて踏んだ）。

## 7. 系統9：入力履歴の表示（解決済み）

### 修正1：ボタンを押した瞬間と押しっぱなしが区別できない

**症状**：ボタンを押しながらレバーを動かすと、入力が変わるたびに新しい列ができるが、押しっぱなしのボタンが**毎回「押した」のと同じ明るいアイコンで再描画**される。押し直したように見えてしまう。

**修正**：ボタン表示を3状態に分けた。

| 表示 | 意味 | 画像 |
|---|---|---|
| 明るい塗りつぶし | そのフレームに押した | `L/M/H_button.png`（既存） |
| **暗い塗りつぶし** | 前から押しっぱなし | `L/M/H_button_held.png`（**新規追加**） |
| 中抜き | そのフレームに離した | `L/M/H_button_release.png`（既存） |

- 既存の`released`（離しの立ち上がり）と同じ仕組みで`pressed`（押しの立ち上がり）を追加。`get_released_buttons()` を `get_button_edges()` に改名し、**両方の立ち上がりを同じ関数内で算出**する（この関数が `prev_buttons` を進めているため、2回に分けると2回目が誤ったフレームと比較してしまう）
- 履歴は「前の列と違うときだけ新しい列を作る」方式なので、**列に保存されるのは先頭フレームのエントリ**。そのため `pressed` は「その列が押しで始まったか」を正しく表す
- `released` と同様、`pressed` は**描画専用**で `is_input_history_entry_equal()` には含めない（列の分かれ方を変えないため）
- `pressed` フィールドが無い古いエントリは従来通り明るく描く（後方互換）

新規画像は既存の`L/M/H_button.png`から**自動生成**（塗り部分を42%に減光、外枠・サイズ・透明部分は元のまま）。生成スクリプトは `make_held_icons.py`。

### 修正2：離しの列が隣の列にはみ出す

**症状**：ボタンをオン・オフで繰り返すと、押しの`●`と離しの`○`が**同じ枠に入っているように見える**。

**原因**：系統2で「離しの列でもボタン領域を描く」ための上書き処理が `draw_input_history_entry()`（描画本体）に追加されたが、**列幅を決めている呼び出し側 `draw_input_history()` には同じ処理が無かった**。

- 呼び出し側：ボタンが1つも押されていない → `idle` と判定 → **22px しか確保しない**
- 描画側：離しがあるので通常の列として扱う → **31px の枠 ＋ 6つのボタンスロットを描く**

差の **9px が隣の押しの列に重なり**、離しの中抜きアイコンが押しの列の上に乗っていた。

**修正**：呼び出し側にも同じ上書き処理を入れ、離しの列にも押しの列と同じ 38px を確保するようにした。

**なお履歴のデータ自体は最初から正しかった**（押しと離しが同居する列は0件）。描画の幅計算だけの問題。

### 調査方法の記録

画面を見るだけでは「隣り合った2列」なのか「1列に両方描かれている」のか区別できなかったため、**履歴のエントリをそのままJSONに出す一時的な計測を入れて確定させた**（各列のフレーム・押されているボタン・押した瞬間・離した瞬間・列のフレーム数）。その実データを呼び出し側と描画側の両方のロジックに通し、離しの列12件すべてが9pxはみ出していること、修正後は0件になることを確認した。計測コードは確定後に削除済み。

## 8. 判明しているメモリ仕様

`base` は P1 が `0xFF8400`、P2 が `0xFF8800`（+0x400 ずつ）。

| アドレス | 内容 |
|---|---|
| `base + 0x001` | キャラが通常状態か。**変身技で 0 になる**（試合の進行状態ではない） |
| `base + 0x004` | 状態ワード。`0x02_00_0E00` なら技が受理される、`0x02_02_0E00` は拒否される |
| `base + 0x005` | やられ・ガード硬直の区分。`0x02` = 硬直中 |
| `base + 0x006` | 実行中アクション。`0x0E` 必殺技 / `0x10` ES / `0x12` EX |
| `base + 0x007` | ゲーム側の受理フラグ |
| `base + 0x00B` | 向き |
| `base + 0x00C` | **被弾/ダウン中に点滅する表示フラグ。`0x00`=表示 / `0xFF`=非表示。リバーサルのpokeで固定されてしまうため、系統5の修正でpoke時に`0x00`へ強制** |
| `base + 0x014` | Y座標（`globals.dummy.p2_y`）。地上の基準値からの相対的な浮き沈みで判定するのが安全（絶対値はキャラ・立ち/しゃがみで変わりうる）。**咎めの穴の発動起点に使用（6章参照）**。旧・系統6章の一部記述では「Y座標での発動は閾値調整が両立せず断念」としていたが、これは**絶対閾値で「空中」と「着地」の両方を判定しようとした旧設計の話**。最終的には「怯み開始時からの相対的な浮き」だけを見て、着地待ちをやめたことで解決した |
| `base + 0x01C` | アニメーション進行ポインタ。技の開始を検出できる |
| `base + 0x122` | ボタン。bit0 LP / bit1 MP / bit2 HP / bit4 LK / bit5 MK / bit6 HK |
| `base + 0x125` | レバー。bit2 下 / bit3 上（絶対）、bit0/bit1 は**向きで左右が入れ替わる** |
| `base + 0x134` | ヒットボックス表示が「無敵」と判定するバイト |
| `base + 0x144` | 連続リバーサルで増えるカウンタ。**画面のHITカウンター表示と連動している（系統7で判明）**。系統7の修正でリバーサルのpoke時に毎回`0x00`へクリア（以前は「クリアするとアニメが消える」と分かっていたが、この用途では実機で問題なし。詳細は系統7参照）。**咎めの穴では、多段の空中コンボで最後のヒットを検知するのにも使用（値の変化＝新しいヒット、6章参照）** |
| `base + 0x147` | 無敵タイマー。ゲーム側が実際にセットするのはpokeの**1フレーム後**。系統8の修正でpoke時（1フレーム早く）にプレースホルダー値`0x01`を書き、翌フレームでゲーム自身が正しい値に上書きする |
| `base + 0x180` | 系統4でクリアしている5バイトの一つ。**`0`→`1`になるのはダウンカウンタ`0x1A7`が動き出す10〜12フレーム前**。ただし後の実測で、これは**実際の着地（Y座標が地上高に戻る瞬間）より20〜24フレームも遅い**ことが判明した（起き上がり許可等、もっと後の合図と見られる）。ダウン終了で`0`に戻り、イントロ中は`0`という性質自体は正しい。**咎めの穴の発動タイミングには現在使っていない（6章参照）** |
| `base + 0x14E` | パレット効果／呪い等。**`0x1C`＝ES（青白い発光）、`0x1E`＝EX（点滅）**。系統6の修正でリバーサルのpoke時に書き込む。`vsavscriptv2.lua`のHUD「CURSED」判定（ワード値`0x0808`）とはビットが重ならず衝突しない |
| `base + 0x174` | リバーサル受付カウンタ。**`9` = 起き上がり、`5` = 硬直から** |
| `base + 0x1A7` | ダウン種別。`0x18`〜`0x1B`。**クリアすると空中復帰できなくなる** |
| `0xFF8009` | 画面種別。`2` = キャラセレ、`4` = 試合中 |
| `0xFF8081` | 内部カウンタ。ターボ3 では表示コマあたり `1,1,2` と進む |
| `0xFF8558` | GC 受付窓のタイマー（通常速度で 14 フレーム） |
| `0xFF9400` | 飛び道具プールの先頭。`0x100` 間隔で 32 個 |


### 特に注意すべき点

## 9. メモリフックが使えることが判明（保留中の可能性）

`memory.registerwrite` / `registerread` / `registerexec` / `getregister` / `setregister` は **FBNeo で動作する**。実機で確認済み。

GitHub の Issue #896 には「動かない」とあるが、ソースを確認すると `src/cpu/m68000_intf.cpp` の 68000 メモリハンドラから `CallRegisteredLuaMemHook` が 11 箇所で呼ばれている（`#if defined (BUILD_WIN32)` 内）。

**実機テストの結果**：内部カウンタ `0xFF8081` への書き込みをフックしたところ、179/180 フレームで 1 表示コマ内に複数回発火。**`emu.registerbefore` が見られない tick で制御を得られることが確定**。

ただし発火回数は 1 コマあたり 4 回で、カウンタの実際の進み（1 コマあたり約 1.33）と一致しない。コマをまたいで値が重複する場面もあり、`0xFF8081` は純粋な tick カウンタではない。**tick の境界を正確に知るには別の基準が必要**。

### これで直せる可能性があるもの

- GC / AG 窓の tick 単位記録（`inputHistory.lua` に作者の TODO あり）
- ターボ時の入力遅延の揺れ（実測 44 回が 1 フレーム、2 回が 2 フレーム）

### 直せなかったもの（tick単位化では、の話）

潰れバグは通常速度でも発生していたため、tick単位化では直らないという判断は正しかった。実際の原因・解決は系統8参照（無敵タイマーをpokeと同フレームで立てる、tickとは無関係の対策）。透明化バグは系統5で解決済み。

テストスクリプトは `hooktest.lua` と `hooktest2.lua`（どちらも観測のみ、書き込みなし。Lua Hotkey 3 で実行）。

- **`0xFF8944` のクリア（`service_held_reversal()`のarm_edge、ダウンにつき1回だけ）** → 透明化バグ対策として再試行。書き込みが効いていることはログで確認済み（poke時のb144が毎回0になった）が、**透明化は直らなかった**。相関はあるが原因ではないと確定
- **`0xFF8920` のクリア（poke時）** → 透明化バグ対策として試行。実機で透明化が繰り返し再現し、効果なしと確定。この時点のログでは正常な回と透明化した回の双方でこのバイトの挙動が同じだったことも後で判明（誤った相関だった）
- **`P1+0x1B7` / `P1+0x1B9` のクリア（poke時）** → コンボ/ヒット数の引き継ぎバグ対策として試行。5回のヒットイベントで`2,3,4,5,7`と綺麗に増える様子から有力候補と判断したが、実機で効果なし。サンプル数が少ないまま「綺麗な増加パターン」だけで確信してしまった失敗例（本当の原因は`0xFF8944`、系統7参照）
- **離し入力を独立した列に分割** → 既存の `remove_nedge_events()` と役割が重複するため取りやめ
- **（メモリpoke方式時代）咎めの穴を Y 座標（`0xFF8814`）で発動させる** → 上昇・下降・閾値5・閾値45と4通り試したが、どれも「空中で出る」か「やられモーションが出る前に発動する」かのどちらかになり両立しなかった。当時は `0xFF8980` の立ち上がりに切り替えて解決したことになっていたが、**これは誤りだった**（下記参照）。当時Y座標が失敗した本当の理由は、pokeがアニメーションを即座に強制するため「絶対的な閾値」でジャストの瞬間を狙う必要があり、精度要求が厳しすぎたこと
- **咎めの穴を `0xFF884C`（`unpushable`）で「ダウンする技」と判定** → 5件のサンプルでは KD=255 / 非KD=0 と綺麗に分かれたが、サンプルを8件に増やすと**全件255**になり無意味と判明。少数サンプルの偽相関
- **（実コマンド入力化後）咎めの穴を `0xFF8980` の立ち上がりで即時投入（unheld）** → 入力履歴には正しく表示されるが技が出ない。後の実測で、この信号自体が実際の着地より20〜24フレーム遅いことが判明（6章参照）
- **同エッジで方向を保持し11フレーム後にボタンを離す（hold+release）** → さらに悪化し、入力履歴に方向すら表示されなくなった。約69フレームもの保持が、入力の生存時間の制約（約10フレーム、`HOLD_LIMIT`）に抵触していたためと考えられる
- **怯み/ガード硬直開始から固定28フレーム後に送信** → 単発ダウン技では正しいタイミングだったが、ダウンしない通常ヒットでも発動し、チェーンコンボでは最初のヒットから数えてしまうため肝心のダウン技ヒットに間に合わなかった
- **`globals.dummy.p2_in_air` の 0→非0→0 で検知** → 全く発動しなかった。ジャンプ状態専用のフラグで、ダウンの吹っ飛びには反応しないと推測される
- **Y座標で「基準+15浮いたら空中」「基準+5以内に戻ったら着地」を検知してから送信** → これも発動せず。最終的には「着地を待つ」のをやめ、「空中を検知した瞬間」から固定フレームで送信する方式（6章参照）で解決した

## 11. 調査手法のヒント

- **成功例と失敗例を、同じ技・同じセッションで揃えて比較する**のが決定的
- **可能ならマークキー（Hotkey 2、系統5で追加）を使い、「見た瞬間」を記録に残す。** 目視の記憶だけに頼ると、どのログがどの事象かの対応付けを誤ることがある（今回の調査でも一度発生した）
- 飛び道具はプレイヤーオブジェクトの外（`0xFF9400`〜）にある
- 記録は **差分圧縮**（初回のみ全体、以降は変化箇所のみ）でファイルが 6 分の 1 程度になる
- アドレスを推測で選ばず、**広域スキャンして差分が出る場所を機械的に特定する**方が速い。「もっともらしい既知アドレス」を先に疑うと遠回りになることがある（系統5では機械的スキャンで見つけた`0xFF890C`が正解で、先に試した2つの推測は外れだった）
- 実機テストによる **二分探索** が有効。8 バイトの候補から 5 バイトを特定した実績あり
- ログは基本的に **1 回のリバーサルにつき 1 ファイル** だが、系統7の調査で `debugKnockdown.lua` の録画開始条件（`was_idle`）を外したため、ニュートラルを挟まない連続リバーサルでは **1 ファイルに複数回のpokeが入る** ことがある。`pokes` 配列を見れば区別できる
- **「差がある」＝「原因」ではない。** 修正を入れて実機で症状が消えることまで確認して初めて確定とする。系統5でも最初の2つの候補（`0xFF8920`、`0xFF8944`）は差分としては見えたが、実際にクリアしても症状が直らず、原因ではなく結果（相関）だった
- **サンプル数が少ないと「綺麗なパターン」に騙される。** 系統7では5件のヒットイベントだけで`2,3,4,5,7`と綺麗に増えるバイトを見つけて有力候補と判断したが実機で外れた。10件に増やして初めて本当の原因（`0xFF8944`）が見つかった。数件の一致だけで確信しない
- **「Aの直前に必ず起きるBを探す」形の走査は強力だが、「直前」の精度は別途検証すること。** 咎めの穴では「ダウンカウンタが動き出す直前に変化するバイト」を全域走査して `0xFF8980` を見つけ、二値信号だからと当初これを発動条件に採用したが、実際には実測着地より20〜24フレームも遅い信号だった。走査で見つかる相関は「近い」の保証であって「同時」の保証ではない
- **観測用ログを取るときは、対象の機能を必ずOFFにする。** 咎めの穴の調査中、その技自体が発動して着地シーケンスを乱し、ログが解析不能になったことがある
- **座標や物理量でタイミングを作ること自体は悪くない。悪いのは「絶対閾値」に依存すること。** 咎めの穴は当初Y座標の絶対閾値（着地判定・上昇判定とも）で4通り試して全滅したが、これはメモリpoke方式（絶対閾値のジャストの瞬間しか許されない）が前提だった。実コマンド入力に切り替えた後、**「怯み開始時からの相対的な浮き」という形でY座標を使い直したところ機能した**。同じ観測量でも、絶対値ではなく直前の基準からの相対変化として使うと閾値のブレに強くなる
- **「入力を送るタイミング」と「技が見た目に発動するタイミング」は別物として扱う。** poke方式では両者が同一（pokeした瞬間に技が始まる）だったため無意識に混同しやすいが、実コマンド入力に切り替えるとゲーム自身が「いつ技を出すか」を決めるようになる。咎めの穴の最終実装では、入力を早めに送っても発動の見た目は毎回ほぼ同じフレーム（着地から10〜12F程度）に揃っており、**入力側は「受け付けられる範囲内で送ること」だけ考えればよく、見た目の精密なタイミング調整は不要だった**
- **少数サンプルの「綺麗な相関」を過信しないのは、原因究明だけでなくタイミング調整でも同じ。** 咎めの穴の`PIT_OF_BLAME_INPUT_DELAY`は当初28で単発ケースは動作したが、実機の別ケースで発動しないことがあり22に調整した。フレーム定数は一度実機で通っても、別の状況でズレが出ることがある

## 13. 系統10：GC input delay（共同開発者の実装、今回マージ）

### 概要

Guard Cancel（GC）は従来、ガード開始を検知すると**最速で** `DPF + (設定ボタン)` を入力していた。これを任意フレーム遅らせ、人間の手入力に近いタイミングでGCを出せるようにする機能。共同開発者が別ブランチで実装したものを、今回の咎めの穴・GC input delay双方の変更を含む `guardCancel.lua` に統合した。**咎めの穴（`'Character Specific Reversal'`）とGC（`'gc'`）は完全に別の `guard_action` 分岐なので競合はない。**

### 背景（既存の `gc_delay` では実現できなかった理由）

既存の共用オプション `gc_delay`（メニュー名「GC/PB/uf/ub/f/b dash cancel delay」）は `make_input_sequence` の `delay_before` で「シーケンス先頭にNeutralを挿入する」方式。GC分岐は `attack_frame = globals.current_frame` で**即座にqueueされる**ため、`gc_delay` は実質「queue開始後にNeutral消費フレームを挟む」だけであり、**入力開始そのものを遅らせることができなかった**。

### 実装

- 新オプション `gc_input_delay`（既定`0`＝従来通り最速）を追加（`config.lua`）
- ガード開始のエッジ（`started_guarding`、1フレームだけ真になるエッジ）で `gc_delayed = { fire_frame = 現在フレーム + gc_input_delay, button = ... }` という**予約**を作る
- `guardCancelCheck()` の先頭、`shouldGC()` の早期returnより前で毎フレーム呼ばれる `service_gc_input_delay()` が、`fire_frame` に到達した時点で `queue_input_sequence()` を直接呼んで入力を開始する
  - `started_guarding` は1フレームエッジなので、GC分岐の `else` で `counter.sequence = nil` にされるロジックとは独立させる必要がある（そうしないと翌フレームで予約が消える）
  - `counter.sequence` / 共通queue経路は通さないため、後続のGC分岐が `sequence` を `nil` にしても予約自体は失われない
- 方針（共同開発者の指定）：遅延カウント中にGC受付窓（blockstun終了）を過ぎても、**予約は破棄せず到着フレームで入力する**
- `gc_input_delay = 0` のときは従来どおり `delay_before` を使わず最速でDPFを送る（Neutral挿入なし）

### メニュー（`menu.lua`）

- 新規「GC input delay」項目（説明文「to simulate human input speed」）。Guard Action Typeが Guard Cancel（`training_settings.guard_action == 2`）のときのみ表示
- 共用の「GC/PB/uf/ub/f/b dash cancel delay」（`guard_action_delay_menu_item`）は、GC選択時は非表示にした（`is_disabled` に `guard_action == 2` を追加）。GC以外（PB / reversal / dash cancel等）への影響はなし

### 要検証（実機）

- 遅延フレームが実際の入力タイミングに正しく反映されること
- 窓外（blockstun終了後）に押した場合、GCではない通常入力としてどう振る舞うか
- 実ハードでのA/Bテスト（共同開発者側でも未実施と記載あり）
