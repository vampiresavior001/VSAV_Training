# 全コマンド対応を見据えたCommand Trainer設計：DI／LIから開始

調査日：2026-10-07。対象ソース：`fc2-v11` / `7745eb19f15cc7961280e07adaa60c493585a107`。
対象ROM：`vsavj`（970519 Japan）。既存のローカルROMとMAME逆アセンブルを使用。
本書は設計・静的解析の成果。トレーナー本体の実装、FBNeoでの実測、GitHubへの反映は未実施。

追加調査：[順押しコマンドのROM調査](SEQUENCE_COMMAND_ROM_SURVEY.ja.md)。
同じ認識器を使う10技の入力列・発動経路を確認し、アナカリスの入力定義と技ID一覧の不整合を記録した。
実装はDI／LI／Midnight Pleasureを先行し、順押し系を優先して広げる。

## 1. 結論と実装の順序

推奨：**ゲームが実際に受理したステップを記録し、入力完成と技発動を別々に確認する。**
先行対象はモリガンのDarkness Illusion（DI）、リリスのLuminous Illusion（LI）、
デミトリのMidnight Pleasureとする。後者のアドレス・入力列は追加調査を参照。
DIとLIは同一の入力テーブルと認識ルーチンを使い、保存先と技発動側の処理が異なる。
GC Command Traceの見た目・Tick記録を参考にするが、GC固有の判定を流用しない。

1. 読み取り専用プローブで、本書のアドレスと受理イベントを実測確認する。
2. 選択した1コマンドについて「受理した入力列・間隔・結果」を表示する。
3. 実測ログで失敗原因の説明を検証してから統計を追加する。
4. 認識器の種類ごとに対応を増やし、最終的に全コマンドへ広げる。

既存GCは維持する。共通化のためだけに最初からguardCancel.luaを大規模改修しない。

## 2. 今回ROMから確認した内容

以下は命令列とデータを照合した静的事実。実行時の表示タイミングは別途確認する。

| 項目 | Darkness Illusion | Luminous Illusion |
|---|---|---|
| キャラID | `0x05` | `0x0E` |
| 技ID（プレイヤー基点+$106） | `0x08` | `0x18` |
| コマンドブロック | 基点+`$330` | 基点+`$348` |
| 判定関数の呼び出し命令 | `0x039802` | `0x04DCFA` |
| 戻り先（BNE命令の直前） | `0x039808` | `0x04DD00` |
| 技ID・状態書き込み後のRTS | `0x0399A2` | `0x04DDA4` |

プレイヤー基点はP1=`0xFF8400`、P2=`0xFF8800`。左右位置とは別概念。
呼び出し前のLEAでA4にブロックが入る。`0x029E7A`はA3に`0x02A6CE`を設定し、
共通認識器`0x02A0C8`へ分岐する。

### 入力テーブル

`0x02A6CE`からのデータ読み取り：`0100 0100 0002 1000 0410`。

| ステップ | 表示 | 比較対象（word & $770F） | 受理後 |
|---|---|---|---|
| 1 | LP | `$0100` | ブロック+1=`$02` |
| 2 | LP | `$0100` | ブロック+1=`$04` |
| 3 | 前 | `$0002` | ブロック+1=`$06` |
| 4 | LK | `$1000` | ブロック+1=`$08` |
| 5 | HP | `$0400` | +0をクリアし、D0=1で返る |

最終wordの`$10`は終端フラグ。最後に+1=`$0A`になるのを待つ実装は誤り。
途中ステップでは`0x02A53A`で+1を2増やす。+0は実行フェーズでありステップ数ではない。
成功・期限切れのどちらでも+0は0になる。+1の古い値も残り得るので、+1だけでは完了判定できない。

### 押し始めと保持の違い

`0x02A0E4`と`0x02A112`はプレイヤー基点+$1ACをwordで読み、期待する値と**完全一致**で比較する。
GCの最後のボタン判定（$1AC OR $1AE）とは異なり、この認識器は$1AEを参照しない。
`0x022208–0x022212`では$1ACを `(~前回の$12A) AND 今回の$12A` で作る。
したがって、これは方向も含む入力の立ち上がりであり、単なる保持状態ではない。

- 2回目のLPには新しいLPの立ち上がりが必要。LPを保持し続けても進まない。
- 前方向にも新しい立ち上がりが必要。最初から前を保持したままでは前ステップが進まない。
- 別のボタン・方向の立ち上がりが同時に含まれると、期待値と一致せずその呼び出しでは進まない。
- すでに保持している別入力と、同時に押し始めた別入力は区別する。
- 途中の不一致は即リセットではなく待機継続（`0x02A118 → 0x02A57C`）。
  「誤入力があったのでそこでコマンド終了」と表示してはいけない。
- 既存Action Stepsの `LP, N, LP, forward, LK, HP` は再生用の入力例。
  Nをコマンドの正式な第2ステップとして表示しない。LPのリリースを詳細履歴に出すのは有用。

上記は内部の正規化済み入力に対する判定。左右入れ替わりや斜めから前への変化は実測で確認する。
特に「前が必要」を「必ずレバー全体をニュートラルに戻す必要がある」と言い換えない。

### 入力完成と技発動は別

共通認識器は入力完成時`0x02A580`で+0をクリアし、D0=1を返す。
期限切れなどのリセットは`0x02A57A`で+0をクリアし、D0=0を返す。

その後、DIは`0x03997E`、LIは`0x04DD80`でゲージ（+$109）を確認し、
`0x02918A`で行動状態などを確認する。条件を満たした経路だけがゲージを減らし、
技IDと状態`0x02001200`を+$04へ書く。

従って次を分ける：

- **Command accepted / 入力成立**：選択した認識器がD0=1で返った。
- **Move started / 技発動**：選択した技の発動書き込み経路に到達した。
- **Accepted; not started / 入力成立・未発動**：入力は成立したが発動条件を満たさなかった。

ゲージ不足は、ゲージ確認分岐時に0だった証拠がある場合だけ断定する。
その他の状態をすべて「硬直中」「キャンセル不可」と一括断定せず、原因未特定を許容する。
技IDの一致だけでは以前の技IDの残留を拾うため、成功判定にしない。

## 3. GC Command Traceから再利用するもの／分けるもの

参照：`scripts/guardCancel.lua`のGC COMMAND TRACE、`scripts/hud.lua`のdraw_gc_command_trace、
`scripts/menu.lua`のShow GC Command Trace、`analysis/test_gc_command_trace.lua`等。

| 再利用候補 | そのまま流用しないもの |
|---|---|
| Tick単位の収集と描画を分ける構成 | ガードが起きるまで表示しない条件 |
| 完了した結果を次の試行まで残す構成 | GC_BLOCKだけのコマンド表 |
| 方向アイコン、ボタンアイコン、警告用オレンジ | GC専用の成功判定・14Tickの窓・再接続条件 |
| 受理された入力間のTick差を表示 | 8行固定や`%256`を前提とした時刻処理 |
| 内部入力とプレイヤー向け表示を分ける考え方 | 前Tickの方向+$125と新しいボタンを無条件に組み合わせる処理 |

現行GCはP1の`0x0221CC`フックで単調増加カウンターを進めている。
このフックは入力正規化・エッジ生成・そのTickのコマンド処理より前にある。
GCと同じ場所でRAMを読むだけでは「いま読んだ入力」と「前回処理した進行」を混同し得る。
新設計では**認識器の呼び出し直前／戻り直後を対にして記録**する。

## 4. 初期プローブの仕様（本体に先行）

DI／LIの観測箇所は表の4アドレス（2キャラ×呼び出し／戻り）と技発動確定2箇所。
Midnight Pleasureは追加調査の呼び出し／戻り／発動確定アドレスを同じ方式で追加する。
共通認識器全体への多数のフックより対象を絞れ、A4やD0を対応づけやすい。
フックは読み取りのみ。レジスタ・RAM・乱数を変更しない。

### 呼び出し前

A6がP1/P2の基点、キャラIDとA4が対象プロフィールに一致する場合だけ採取する。
プレイヤーごとの単調増加Tick、Tick内のイベント連番、A4、+0/+1/+4、$1AC/$1AE、
$12A/$12C、$394、向き+$0B／+$120、+$04..$07、技ID+$106、ゲージ+$109を保存する。
押下・保持・離しを別データとして残す。実際の判定に使うのは呼び出し時の$1AC。

### 戻り直後

対応する呼び出しがあることを確認し、D0と+0/+1/+4を取得する。

1. D0=1なら最終ステップ受理＋Command acceptedを記録。
2. それ以外で+1の正規の増分があれば、中間ステップ受理を記録。
3. 入力待ちフェーズから+0=0へ戻り、タイマー減算が0に達した経路ならExpiredを記録。
4. 判定ルーチン未実行や外部リセットはExpiredにせず、別イベントとして扱う。

最終ステップは+1が増えないため、1を先に判定する。
初回LPは+1の古い残留値があっても+0=0からの開始として扱い、新しい試行を作る。
同じTickの入力成立→発動条件不成立→別技成立もイベント連番で順序を保存する。

### 技発動確認

`0x0399A2`／`0x04DDA4`のRTS直前で、対象プレイヤー・キャラ・技ID・状態を確認する。
直前の入力成立イベントと対応させる。入力注入や直接状態変更で技が出ただけの場合は
人のコマンド入力成功に加算しない。初期計測ではダミー自動操作をOFFにする。

### フックと時刻の注意

- registerexecは命令実行前。書き込み命令そのもののPCで書き込み後の値を読もうとしない。
- 既存の`0x0221CC`や`0x02211A`へ別のregisterexecを重ねて既存処理を上書きしない。
  時刻採取を統合する場合は既存コールバックから観測関数を呼ぶ形を検討する。
- P2用にも独立したカウンターを用意。左右位置とP1/P2を混同しない。
- Tickは内部更新回数、timeout値は認識器の処理回数。停止中などに両者が一致するか測定する。
- Turbo3で表示1フレーム中に複数の更新があっても、全イベントを採る。
- セーブステート読み込み、リセット、キャラ変更、ラウンド遷移でepochを切り替える。
  途中で有効化した場合は途中採取とし、不完全な入力列を成功率の分母に入れない。
- 対象ROMと命令シグネチャを確認できない場合は監視を無効にする。
  Luaの通常memory.readwordが復号命令を返すとは限らず、そのAPIでのシグネチャ検証方法も要確認。
- Run-aheadはDisabledで検証する。

## 5. 画面と練習の設計案

名称は **Command Trainer**。履歴表示は **Command Trace**。
GC Command Traceと混同しないよう、対象技名を表示する。
設定候補：`Command Trainer: Off / On`、`Player: P1 / P2`、`Command: <技名>`、
`View: Compact / Detailed`。設置先は既存メニュー階層・表示面積を確認して決める。
初期版は自動技推定ではなく技を選択する。共通のLP始動を誤って別技の試行と数えないため。

通常表示は「技名」「5ステップと間隔」「結果」の小さなパネルとする。
受理済みは明るく、待機中は強調、未到達は暗くする。
前はゲームの正規化入力として保持し、表示では受理時の向きに対応した左右矢印を使う。
長い技名は全名を設定画面へ、HUDではDI／LIなどの略称も検討する。
GCと重なる位置に二重描画せず、同じ表示枠を切り替える案を優先する。

結果の読み方：

| 表示例 | 意味と練習への用途 |
|---|---|
| `Waiting: LP (2)` | 2回目のLPをまだ受理していない。保持／離し／再押下を詳細で確認 |
| `Waiting: Forward` | 前方向のステップをまだ受理していない。前保持と前への変化を比較 |
| `Expired before LK` | LKを受理する前に期限切れ。直前の前入力からの間隔を確認 |
| `Command accepted / Move started` | 入力完成と技発動の両方を確認 |
| `Command accepted / No meter` | 入力は正しく、発動時のゲージ確認で止まった証拠がある |
| `Command accepted / Not started` | 入力は正しいが未発動。原因が未特定ならそのまま表示 |

詳細表示では「実入力」と「受理イベント」を別行で比較する。
例えばLP+MPの同時押しで受理が進まなかったことは表示できるが、
同じ試行で後から正しいLPを入力して進んだ場合は試行全体を失敗にしない。
画面は直前の完了結果を保持し、次の有効な第1ステップを受理したら切り替える。
任意の短いタイマーで結果を消さない。詳細確認中は結果を固定できるとよい。

時間表示は第1入力を0tとする経過Tickと、受理入力間の差。最後−最初をInput tとする。
両端を含む入力占有Tick数とは別なので、必要なら別名称で表示する。
生タイマー値をそのまま「残り入力可能Tick」と説明しない。
警告は既存と同じオレンジを使えるが、GCの12t閾値は未検証で流用しない。
初期版は間隔の実数と実際の期限切れ箇所を示し、「遅い」の閾値は実測後に決める。

統計は後段：入力成立率と技発動率を分け、ゲージ不足を入力失敗にしない。
分母は選択技の第1ステップをゲームが受理した試行。途中中断・モード変更は除外する。
最初のLPすら受理されなかった操作は通常の試行数から漏れるため、詳細履歴で確認可能にする。
各段の到達数と期限切れ位置が、総入力Tickの平均だけより改善点を見つけやすい。

## 6. 全コマンド対応の構成

プロフィール（技とROMアドレス）、観測、認識器別解釈、試行管理、描画を分ける。
既存charMoves.luaは技名／技IDとの連携に使えるが、再生入力列を認識仕様の根拠にはしない。

プロフィール項目案：rom_set、character_id、move_id、表示名、recognizer_kind、
block_offset、table_address、call_sites、completion_signal、move_start_signal、
verification_status、根拠ファイル。単に「同じコマンド」だけで別技を統合しない。

| 認識器の種類 | 拡張時に必要な観測 |
|---|---|
| 順押し（今回） | 押下エッジとステップ、最終戻り値 |
| 方向列＋ボタン | 方向受理、押し／離しの許容、最終ボタン |
| ボタン＋方向・同時押し | 部分一致／完全一致、同時押し条件 |
| タメ | タメ蓄積、方向を離した後の猶予、完成後のボタン待ち |
| 360／720 | 認識器の方向履歴・回転進行。+1増分の方式を決めつけない |
| 連打 | ボタンごとの蓄積回数、時間切れ、強度 |
| 派生・状態依存 | 始動技／空中／Dark Forceなどの前提状態、技の優先順位 |

ROM内に複数の呼び出し経路がある技は全経路を列挙する。
選択中のコマンドが別技の優先判定により評価されなかった場合は「未評価」とし、
勝手に仮想のタイマーを進めない。
対応状態を「未解析／静的確認／実機確認」に分け、未対応技を対応済みとして選択させない。
全コマンド対応は段階的な目標であり、全技が今回の5ステップ形式で扱えるという意味ではない。

## 7. 未確定事項と検証表

**猶予の固定値はまだ確定しない。** `0x02A53A–0x02A54E`は乱数を用いてタイマーを再設定する。
手元の逆アセンブルでは`0x02A55A`に14〜19が見えるが、同じ場所の生ROMデータは異なる。
命令のPC相対読み取り経路を含むメモリビューの確認が必要。
既存のVSAV_REFERENCE.mdにもこの表はlisting読み依存と注意がある。
今回の証拠JSONには両ビューを残す。実機で+4への書き込み結果、減算、受理限界を採り、
「表の値」「判定呼び出し回数」「人が入力できる間隔」を分けて確定する。
入力テーブル`0x02A6CE`はA3経由のデータ読み取りなので、生ROMのwordを使用した。

| 検証 | 合格条件 |
|---|---|
| DI／LI、P1／P2、左右 | 表示した受理入力と向きが内部判定・ログに一致 |
| LP保持→離し→再押下 | 保持だけでは2段目へ進まず、再押下で進む |
| 前保持／前への変化 | 保持と新しい方向エッジを区別できる |
| 余分な同時押し／途中の誤入力 | 不受理と即終了を混同せず、その後の成功も追える |
| 最後のHP | +1が増えなくても入力完成を採れる |
| ゲージ有／無、通常技中・やられ中 | 入力成立と発動条件を分ける |
| 各ステップの猶予境界・複数乱数状態 | 実際の期限切れとその時点の待機ステップを一致させる |
| Normal／Turbo3、停止・ヒットストップ | 描画フレームに依存してイベントを落とさない |
| 素早く2回連続、向き反転、相手越え | 試行IDと入力方向を取り違えない |
| リセット・ロード・途中有効化 | 以前の試行に結合せず、偽の失敗を集計しない |
| 既存GC・記録／再生・Action Steps併用 | 既存フックを壊さず、自動操作を人の成功と混同しない |

## 8. 再現資料とClaudeへの引き継ぎ

- `extract_illusion_commands.py`：命令シグネチャと入力テーブルを再確認する読み取り専用ツール。
- `illusion_command_evidence.json`：今回の実行結果、対象データのハッシュ、アドレス、未確定タイマー情報。
- 既存資料：`vsav_tool.py`、`VSAV_REFERENCE.md`、`COMMAND_TABLE.md`。
- 既存表示：`vsavscriptv2.lua`には両技の進行表示があるが、最終判定の完全な根拠として扱わない。
- `COMMAND_TABLE.md`では両キャラが「抽出できず」になっているため、それを全コマンド表の完成版と扱わない。

再現コマンド（パスは手元の配置に合わせる）：

```sh
python analysis/extract_illusion_commands.py --code-dir /path/to/mame_code --rom-zip /path/to/vsavj.zip > analysis/illusion_command_evidence.json
```

Claudeへの依頼：まず本書と証拠JSONを照合し、読み取り専用プローブを作る。
特に最終戻り値・実際の発動・前方向エッジ・猶予の4点を実機ログで確認する。
その結果をanalysisへ追記したうえで、小さな選択式Command Trainerを実装する。
結果画面の表示面積を確認し、既存GC表示は壊さず、判定ロジックの共通化は後段にする。
未確認の原因や対応していない技について、推定の成功／失敗を表示しない。

ROM本体や広範な逆アセンブルは成果物に含めない。今回追加したのは解析文書、抽出ツール、
小さな派生データのみ。既存実装・UI・保存形式は変更していない。
