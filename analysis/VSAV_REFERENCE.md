# ヴァンパイアセイヴァー エンジン リファレンス

`VSAV_ENGINE.md` は作業ログで、途中で捨てた仮説や誤りをそのまま残してある。
**この文書はそこから確定事項だけを取り出し、誤りを訂正して整理した最終版**である。

## 0. 読み方と信頼度の表記

各項目には根拠を必ず付ける。根拠の種類を次の3つに分ける。

| 記号 | 意味 |
|---|---|
| **ROM** | 逆アセンブルの命令そのもの。アドレスと命令を併記する |
| **DUMP** | ゲーム実行中に `memory.readbyte` で読んだ ROM データ |
| **実測** | ログの統計。件数を併記する |

**逆アセンブル(`analysis/mame_code/`)はオペコード空間のダンプである。**
CPS2 はプログラム ROM を暗号化しており MAME はオペコードだけを復号するので、
**コードは正しく逆アセンブルされるがデータテーブルは全て化ける。**
判別法: 既知の attack テーブル 0x0764EA の +5 バイトは 0/1/2 しか取り得ないのに、
listing では 226/126/253 と読める。

したがって **データは必ず DUMP で採る。** `analysis/rom.py` は listing から
バイトを読むが、これは**コード領域にしか使えない**。

表記: `$xxx` は A6 相対のオブジェクト内オフセット。
P1 のオブジェクトは 0xFF8400、P2 は 0xFF8800。以降 P2 の絶対アドレスを併記する。

「ティック」= ゲームの内部処理 1 回。「フレーム」= 表示 1 枚 = Lua コールバック 1 回。
**この2つは 1 対 1 ではない。** 起き上がり中の実測で **1 フレームあたり約 1.6 ティック**
(スパン内 2445 ティック遷移のうち 1482 がフレーム境界を跨ぐ)。
**フレーム側のコードは 4 割のティックを見ていない。** これが v99〜v131 の
失敗のほとんどの根本原因だった。

`$06` の行動カテゴリ(実測で確定したもの):

| 値 | 意味 | | 値 | 意味 |
|---|---|---|---|---|
| 0x00 | 待機 / インパクトフリーズ | | 0x0E | 必殺技 |
| 0x02 | **多義**(やられ硬直 / 投げ / Q-Bee の自由状態) | | 0x10 | ES |
| 0x04 | **free の 1 ティック前** | | 0x12 | EX |
| 0x06 | ジャンプ | | 0x14 | ダッシュ |
| 0x08 | 空中(ジャンプ中) | | 0x16 | ダークフォース |
| 0x0A | 通常技 | | 0x1A | **ダークフォース停止** |
| 0x0C | **ガード** | | | |

0x1A は画面表示(`ACT 1A`)から確定した。
**0x02 は名前を付けられない** — やられ側の硬直でもあり、投げでもあり、
Q-Bee は自由なまま 0x02 に居るので、少なくとも 3 つを 1 つの番号が兼ねている。
名付けると誤ラベルの方が多くなるため、番号のまま表示する。
**ROM から網羅するのは安くない** — `move.b #imm, ($6,A6)` は
プログラム全体で 10 箇所しかなく、残りは `addq` と `move.l` の
一括書き込みを通る。未知の値は番号のまま表示してログに残す方式にしてある(§8.4)。

キャラクタ ID(`charMoves.lua` の `get_character()` が正):

0x00 Bulleta / 0x01 Demitri / 0x02 Gallon / 0x03 Victor / 0x04 Zabel /
0x05 Morrigan / 0x06 Anakaris / 0x07 Felicia / 0x08 Bishamon / 0x09 Aulbath /
0x0A Sasquatch / **0x0B Zabel(2つ目の枠)** / 0x0C Q-Bee / 0x0D Lei-Lei /
0x0E Lilith / 0x0F Jedah / **0x12 Dark Gallon** / **0x18 Oboro**

**0x0B は 0x04 と同じ「Zabel」を返す。**別名ではなく同じキャラの 2 つ目の枠で、
アニメスクリプト表も 0x04 と同一である。解析ツールで `Zabel2` と書いているのは
**ID を区別するためのラベルで、キャラクタ名ではない。**

**ID は 0x0F で終わらない。** 0x12 Dark Gallon と 0x18 Oboro があり、
`kd_report.py` などの名前表が 0x0F までしか無いと**名前無しで落ちる**。

## 2. 1ティックの入力処理

**ROM 0x02207E〜0x022130。** 順序が全ての土台なので命令ごと引く。

```
02209A: 4EB9 0001 4E8A  jsr     $14e8a.l        ; 入力ステージ2。$394 を埋める
0220A0: 0800 0000       btst    #$0, D0
0220A4: 6626            bne     $220cc          ; P2 を先に処理する分岐
0220A6: 4DED 0400       lea     ($400,A5), A6   ; P1
0220AA: 6100 0068       bsr     $22114
0220B4: 4DED 0800       lea     ($800,A5), A6   ; P2
0220B8: 6100 005A       bsr     $22114
```

**0x022114 はプレイヤーごとに 1 ティック 1 回だけ呼ばれる。**
どちらを先に処理するかは切り替わる。

```
022114: 3D6E 0122 0124  move.w ($122,A6), ($124,A6)   ; 前回値を退避
02211A: 3D6E 0394 0122  move.w ($394,A6), ($122,A6)   ; ★ $394 -> $122
022120: 3D6E 012A 012C  move.w ($12a,A6), ($12c,A6)
022126: 3D6E 0394 012A  move.w ($394,A6), ($12a,A6)   ; ★ $394 -> $12a
02212C: 6100 0012       bsr    $22140                 ; $32 = 相手, $108
022130: 6100 002E       bsr    $22160                 ; $120 = 実際の左右
022134: 6100 0058       bsr    $2218e                 ; 向き反転とエッジ
```

**`$394` は 1 ティックに 2 か所へ複写される。**
`0x02211A` の直前に `$394` へ書けば `$122` と `$12a` の両方に届く。
これがツールの注入が成立する根拠である。

### 2.1 向き反転が2種類ある

```
02218E: 4A2E 000B       tst.b  ($b,A6)        ; $122 側は $b だけで決まる
022192: 6716            beq    $221aa
022194: 302E 0122       move.w ($122,A6), D0
022198: 0240 0003       andi.w #$3, D0
02219C: 103B 002A       move.b ($2a,PC,D0.w), D0   ; 表 = 0x0221C8
0221A0: 026E FFFC 0122  andi.w #$fffc, ($122,A6)
0221A6: 816E 0122       or.w   D0, ($122,A6)
0221AA: 302E 0124       move.w ($124,A6), D0
0221AE: 4640            not.w  D0
0221B0: C06E 0122       and.w  ($122,A6), D0
0221B4: 3D40 0126       move.w D0, ($126,A6)          ; 押した瞬間
0221B8..0221C2:                                       ; $128 = 離した瞬間

0221CC: 102E 000B       move.b ($b,A6), D0            ; $12a 側は条件が違う
0221D0: 4A2E 0038       tst.b  ($38,A6)  / bne -> $b
0221D6: 4A2E 0115       tst.b  ($115,A6) / bne -> $b
0221DC: 102E 0120       move.b ($120,A6), D0          ; どちらも 0 なら $120
0221E0: 4A00            tst.b  D0 / beq -> 反転しない
0221E4..0221F6:                                       ; $12a を同じ表で反転
```

反転表 0x0221C8 = `00 02 01 03`(bit0 と bit1 の入れ替え)。
listing 上のデータなので **DUMP 対象**(v133 で採取するようにした)。

**コマンド認識が読むのは `$12a` なので、方向を作る側もこちらの規則に従う必要がある。**
`guardCancel.lua` の `facing_for_input()` は既にこの規則(`$38`/`$115` が
立っていれば `$b`、それ以外は `$120`)で書かれている。

レバービット(`$394` の下位バイト): `0x01` bit0 / `0x02` bit1 / `0x04` 下 / `0x08` 上。
bit0 と bit1 のどちらが前かは上記の反転で決まる。ボタンは上位バイト。

## 3. コマンド認識

### 3.1 ディスパッチ

```
026144: 102E 0382       move.b  ($382,A6), D0   ; キャラクタ ID
026148: 4880            ext.w   D0
02614A: E548            lsl.w   #2, D0
02614C: 207C 000B D3FA  movea.l #$bd3fa, A0     ; ★ コマンド表(起き上がり表とは別)
026152: 2070 0000       movea.l (A0,D0.w), A0
026156: 4E90            jsr     (A0)
```

**0x0BD3FA がコマンド認識の表、0x0BD47A が起き上がりの表。**
この2つを取り違えると別キャラの技を読むことになる(過去に実際にやった。§10)。

マッチャは 5 種類。
`0x029F4A` 通常の方向列 / `0x02A030` ボタン+方向 / `0x02A0C8` /
`0x02A1B4` 回転 / `0x02A2EA` 溜め。

### 3.2 方向の歩(0x029F4A)

```
029F60: 3213            move.w (A3), D1           ; コマンドデータの歩
029F64: 0241 000F       andi.w #$f, D1
029F68: 302E 012A       move.w ($12a,A6), D0      ; ★ $122 ではない
029F6C: 0240 000F       andi.w #$f, D0            ; ★ 方向4ビットだけ
029F70: 0806 0007       btst   #$7, D6
029F74: 6608            bne    $29f7e
029F76: B041            cmp.w  D1, D0             ; ★ 完全一致
029F78: 6600 0600       bne    $2a57a
029F7E: C041            and.w  D1, D0             ; bit7 が立つ歩はマスク一致
029F84: 5414            addq.b #2, (A4)           ; 1歩進む
```

* **bit7 が立っていない限り完全一致。**「下」を要求する歩に「下前」は通らない。
* **ボタンビットは `andi.w #$f` で捨てられる。**最後の方向とボタンを同時に
  入れても方向判定を壊さない。
* 進行状態は (A4)。**成功も失敗も `clr.b (A4)` でリセットされる**
  (0x02A57A 失敗 D0=0 / 0x02A580 成功 D0=1)。

ボタンの歩は `$1ac`(押した)と `$1ae`(離した)を読む(0x029FEC)。

### 3.3 歩ごとのタイムアウト

```
02A524: 542C 0001       addq.b #2, ($1,A4)
02A528: 4EB9 0001 4E8A  jsr    $14e8a.l          ; 乱数
02A52E: 0240 001F       andi.w #$1f, D0          ; 0..31
02A532: 197B 0026 0004  move.b ($26,PC,D0.w), ($4,A4)
...
029F96: 532C 0004       subq.b #1, ($4,A4)
029F9A: 6700 05DE       beq    $2a57a            ; 0 になったら motion 全消し
```

`move.b ($26,PC,D0.w)` の EA = 0x02A534 + 0x26 = **0x02A55A**。
表の値は **0x0E〜0x13 = 14〜19 ティック**(listing 読みなので DUMP 対象)。
**歩ごと**であり、切れるとモーション全体が失われる。

### 3.4 1ティックの入力で 1 歩進むか

**ROM だけでは断定できない。** 0x026144 の呼び出し元がジャンプテーブル経由で、
そのテーブルはデータ領域にあり listing では追えない。

**実測が答えている:** サスカッチの HCB は 4 エントリで、
**4 連続ティックに 1 つずつ入れた 7 スパンが 7/7 成立した。**
判定が毎ティック走っていなければ 1 ティックのエントリは見逃され、
4 歩のコマンドは絶対に完成しない。

### 3.5 コマンドの形(DUMP、0x02A610 のデータを復号して読んだもの)

| 名前 | 歩 | 数 |
|---|---|---|
| QCF | 下、下前、前 | 3 |
| QCB | 下、下後、後 | 3 |
| DPF | 前、下、下前 | 3 |
| HCF | 後、下後、下、**下前** | 4 |
| HCB | 前、下前、下、**後** | 4 |
| 360 | 4 方向すべて。開始はどこからでもよい | 4 |
| 720 | 360 を 2 周 | 8 |

**HCF は前で終わらない。HCB は HCF の鏡像ではない。**
**最初の方向もコマンドの一部である**(以前これを落としていた。§10)。

回転コマンド(0x02A1B4)は `$394` を直接読み、`cmpi` で 4 方向とだけ比較する
ので**斜めは弾かれる**。開始位置が記録され、隣接方向へ 1 つずつしか進まない。

## 4. ダウンと起き上がり

### 4.1 `$140 = 0x0A` になる場所

0x027D5A ただ 1 箇所。`$26`(やられ時間)が 0 になった後、
`$50`/`$52`(速度)の分岐から 8 経路で到達する。
`$26` は `$54` を添字にした表 0x028BE0 / 0x028C40 / 0x028CA0 から入る。

**`$54` はヒットした瞬間に確定する**ので、
**その技がダウンさせる技かどうかはヒット時点で判る。**
実測で 0x05 と 0x49 がダウン、4 は空中復帰(`$117` が立つと 4→5 に書き換わる、
ROM 0x023A54)。

### 4.2 `$1a7` は「毎ティック +1」だが無条件ではない

```
024E78: 4A2D 015D       tst.b  ($15d,A5)
024E7C: 661E            bne    $24e9c          ; rts。+1 されない
024E7E: 4A2E 0194       tst.b  ($194,A6)
024E82: 661A            bne    $24e9e          ; jmp。+1 されない
024E84: 522E 01A7       addq.b #1, ($1a7,A6)   ; ★
024E8A: 102E 0382       move.b ($382,A6), D0
024E8E: E548            lsl.w  #2, D0
024E90: 207C 000B D47A  movea.l #$bd47a, A0    ; ★ 起き上がりハンドラ表
024E96: 2070 0000       movea.l (A0,D0.w), A0
024E9A: 4ED0            jmp    (A0)
```

止まるときは**ハンドラごと飛ぶのでアニメも進まない。**
「終端 `$1a7` = アニメの長さ」の関係は保たれる。
実測でも起き上がり中は 2445/2445 で +1 だった。

**`$1a7` が終端値と比較される箇所は ROM に存在しない。**
唯一の比較 0x027B06 は `cmpi.b #$4, ($1a7,A4)` で、A4 は**相手**のオブジェクト
であり別用途。**`$1a7` は結果を数えているだけの傍観者である。**

### 4.4 汎用ハンドラの中身

`$07` で再ディスパッチする。

```

024EA8: 323B 0006       move.w ($6,PC,D0.w), D1
024EAC: 4EFB 1002       jmp    ($2,PC,D1.w)      ; EA = PC+2+D1
```

**`$07 = 0x00`(ダウンした直後、その場か移動かを決める)**

```

024EBC: 6700 003A       beq    $24ef8            ; $a == 0 -> その場
024EC0: 6B00 001C       bmi    $24ede            ; $a < 0  -> 移動(前)
024EC4: 1D7C 0004 0007  move.b #$4, ($7,A6)      ; $a > 0  -> 移動(後)
024ECA: 2D7C FFFA 0000 0040   move.l #$fffa0000, ($40,A6)
024ED8: 7045            moveq  #$45, D0          ; アニメ 0x45
024EDA: 6000 2FE4       bra    $27ec0
024EDE: 1D7C 0004 0007  move.b #$4, ($7,A6)
024EE4: 2D7C 0006 0000 0040   move.l #$60000, ($40,A6)
024EF2: 7047            moveq  #$47, D0          ; アニメ 0x47
024EF8: 542E 0007       addq.b #2, ($7,A6)       ; $07 := 2
024EFC: 7044            moveq  #$44, D0          ; ★ アニメ 0x44 = その場起き上がり
```

```
024F1C: 4E75            rts
```

**`$07 = 0x04` → `0x06` → `0x02`(移動起き上がり)**

```
024F1E: 4A2E 0021       tst.b  ($21,A6) / bne $27f70   ; $21 == 0 待ち
024F26: 542E 0007       addq.b #2, ($7,A6)             ; $07 := 6
024F2A: 4A2E 000B       tst.b  ($b,A6) / neg.l ($40,A6) ; 向きで速度反転
024F38: 4A2E 0021       tst.b  ($21,A6) / bmi $24f4c   ; 負になるまで
024F40: 202E 0040       move.l ($40,A6), D0
024F44: D1AE 0010       add.l  D0, ($10,A6)            ; 転がりながら X を加算
024F4C: 1D7C 0002 0007  move.b #$2, ($7,A6)            ; ★ $07 を 2 に戻す
024F52: 7048            moveq  #$48, D0
024F54: 4A2E 000A       tst.b  ($a,A6) / bmi
024F5A: 7046            moveq  #$46, D0                ; $a の符号で 0x46 / 0x48
024F5C: 6000 2F62       bra    $27ec0
```

**移動起き上がりは最後に `$07` = 2 へ合流し、その場と同じ `$21` 判定で終わる。**
だから終端値は「転がりアニメ + 起き上がりアニメ」の合計になる。

キャラ固有ハンドラも同型。`$07 = 0x02` の終了判定は全て `tst.b ($21,A6)`:
Gallon 0x033502 / Morrigan 0x039172 / Lilith 0x04DBBA / Bishamon 0x042F92。

### 4.5 free-1 のシグネチャ

`move.l #$2020400, ($4,A6)` は `$04=0x02 / $05=0x02 / $06=0x04 / $07=0x00` を
一括で書く。**この状態は 1 ティックしか続かず、次のティックで必ず free になる。**
実測: 巻き戻しを除いた時間軸で 69/69。

実際に `$05` が 0x00 になるのはさらに次の段階:

```
026D54: 2D7C 0200 0000 0004  move.l #$2000000, ($4,A6)
026D72: 2D7C 0200 0004 0004  move.l #$2000004, ($4,A6)
026D8A: 2D7C 0200 0002 0004  move.l #$2000002, ($4,A6)
```

### 4.7 Q-Bee は free-1 の前状態を通らない

全キャラで free-1 のシグネチャ(`$06 = 0x04`)の出現率を数えると、
**Q-Bee だけ 0/21、他の 13 キャラは 249/250**。

ハンドラ 0x04A6FA の `$07 = 2`:

```
04A764: 4EB9 0002 7F70  jsr    $27f70.l        ; アニメを進める
04A76A: 4A2E 0023       tst.b  ($23,A6)        ; ★ $21 ではなく $23
04A76E: 6A42            bpl    $4a7b2          ; まだ回復中 -> rts
04A780: 4A2E 03B4       tst.b  ($3b4,A6)
04A784: 6624            bne    $4a7aa          ; ← ここだけがシグネチャへの経路
04A7A0: 2D7C 0200 0002 0004  move.l #$2000002, ($4,A6)   ; ★ 通常の出口
04A7AA: 2D7C 0202 0400 0004  move.l #$2020400, ($4,A6)   ; $3b4 が非0 のときだけ
```

`$3b4` は実測で 0 なので、**彼女は `$05=00 / $06=00` を 1 命令で書いて
free になる。**中間状態が存在しない。

さらに `024E84` は**ハンドラより前**に `$1a7` を +1 するので、
**Q-Bee の「終端 `$1a7`」は free-1 ではなく free そのもの**である。
他キャラより 1 ティック遅い値が記録されている。

終端は `$a` の符号で 3 通りに割れ、実測と厳密に対応する:

| `$a` | アニメ | 実測終端 |
|---|---|---|
| 0(その場) | 0x44 | 15 |
| > 0 | 0x45 → 0x46 | 40 |
| < 0 | 0x47 → 0x48 | 47 |

24 ティックの転がりは `04A748 move.b #$18,($26,A6)` の固定タイマである。

**つまり不可能ではない。**シグネチャではなく**時計で撃つ**必要がある、というだけ。
v160 で実装した:

* `KD_NO_SIG` に 0x0C を入れ、**最後のエントリ(ボタン付き)もティックフックが置く**。
  他キャラはシグネチャ任せのままである。
* 3 種の起き上がりは **`$a` の符号**で決まる。`$07` でも `$27` でもない。

| `$a` | 起き上がり | 終端 `$1a7` |
|---|---|---|
| 0 | その場 | **15** |
| < 0 | ロール | **40** |
| > 0 | ロール | **47** |

実測 43 スパンで例外なし。`$07` は分離しない(`$a` > 0 が `$07` = 2 でも
4 でも出る)。`$27` は ROM がアニメ ID を入れる場所だが(0x04A74E)、
**`$1a7` が 1 になるティックではまだ 0** — 同じパスの後半で書かれるためである。
v161 は `$27` を鍵にしたので照合が一度も成立せず、ロールだけ `$21` 規則に
落ちて何も出なかった。その場だけ完璧だったのはそのため。

**そして彼女の必殺技は構造上 free+1 が最速である。**
その場起き上がりは 13/13 で `+1` に出た。他キャラの free+0 には届かない。
`KD_NO_SIG` のキャラは表示の下限も 1 に上げてあるので、`+1F` ではなく
`FASTEST` と出る。

**そしてボタンは他キャラより 1 ティック遅い**(v162)。

2 つの位置を試して両方とも不発だった —
v160 は終端(トレース上の free−1、他キャラのボタンの位置)、
v161 はその 1 つ前。モーション自体はどちらも完璧に入っていた
(下・下前・前+ボタンが 3 連続ティック)のに `$06` は free を通して 0x00 のまま。

**原因は入力窓 `$174` が開く位置**である。他キャラはシグネチャの直後:

```
024F0A: move.l #$2020400, ($4,A6)
024F12: move.b #$5, ($174,A6)      ← free-1 で既に開いている
```

Q-Bee は出口の中で開く:

```
04A77C: addq.b #5, ($174,A6)
04A7A0: move.l #$2000002, ($4,A6)
```

0x024E84 のハンドラは**そのティックの入力が複写された後**に走るので、
**窓が開くティックには認識器はもう見終わっている。**
そこで押しても座る場所が無い。

したがって彼女のボタンは**その次のティック、すなわち free のティック**に置く。
通常技が全キャラで持っている関係(§8.5)と同じである。
終端は測定値の 15 / 40 / 47 に戻し、最後のエントリは
**通常技と同じ遅延押し経路**に渡す(新しい定数ではなく、既に動いている仕組み)。

### 4.6 デミトリだけ例外 ― 終わりが物理

```
031050: 542E 0007       addq.b #2, ($7,A6)      ; $a によらず必ず $07 := 2
0310CA: 4A2E 0021       tst.b  ($21,A6)
0310CE: 660A            bne    $310da           ; bpl ではなく bne
```

## 5. アニメーションスクリプト

### 5.1 読み込み

```
027EC0: 207C 000B CF7A  movea.l #$bcf7a, A0       ; キャラ別スクリプト表(long)
027ECE: 122E 0382       move.b  ($382,A6), D1
027ED4: E549            lsl.w   #2, D1
027ED6: 2070 1000       movea.l (A0,D1.w), A0     ; そのキャラのスクリプト一覧
027EDA: 0240 00FF       andi.w  #$ff, D0          ; アニメ ID
027EDE: D040            add.w   D0, D0
027EE0: 3030 0000       move.w  (A0,D0.w), D0     ; ワードオフセット
027EE4: 41F0 0000       lea     (A0,D0.w), A0
027EE8: 2D48 001C       move.l  A0, ($1c,A6)
027EEC: 2D50 0020       move.l  (A0), ($20,A6)    ; $20=セル長 $21=セルフラグ
```

`0x027EC8` から入ると表は 0x0BCE7A、`0x027FA2` からだと 0x0BCFFA。

### 5.2 進行

```
027F70: 532E 0020       subq.b  #1, ($20,A6)      ; セルを1ティック消化
027F74: 6628            bne     $27f9e
027F76: 206E 001C       movea.l ($1c,A6), A0
027F7A: 1028 0001       move.b  ($1,A0), D0       ; フラグ
027F7E: 6716            beq     $27f96            ; 0    = 次のセル
027F80: 6B0C            bmi     $27f8e            ; bit7 = ジャンプ
027F82: 0800 0006       btst    #$6, D0
027F86: 670E            beq     $27f96
027F88: 50EE 0021       st      ($21,A6)          ; ★ bit6 = 終端 -> $21 = 0xFF
027F8E: 2068 0018       movea.l ($18,A0), A0      ; ジャンプ先
027F96: 41E8 0018       lea     ($18,A0), A0      ; ★ 次のセルは 24 バイト先
```

**プレイヤーオブジェクトのセルは 24 バイト。**+0 が長さ(ティック)、+1 がフラグ。

**注意: セル長の異なる同型ルーチンが他にもある。**
0x015030 は 8 バイト/セル(ジャンプ先は +8)、0x01505A も別系統。
**起き上がりハンドラが `bpl` で飛ぶ先は 0x027F70 なので、
プレイヤーの起き上がりは 24 バイト版である。** DUMP でも 24 バイト刻みで
全 16 キャラ × 5 アニメが bit6 で正しく終端し、下記の法則が成立した。

### 5.3 `$21` の正体

**`$21` はスクリプトのフラグバイトそのものである。**
`$21 == 0x40` は「終端セルが再生中」を意味するだけで、
**終端セルの長さはキャラごとに違う**(ガロン 1 ティック、モリガン 3)。
`$21 == 0x40` を起点にした arm がキャラを変えると崩れたのはこれが理由。

### 5.4 起き上がりの長さは ROM から出る

**DUMP + 実測:**

| キャラ | anim44 合計 | 実測終端 `$1a7` | 差 |
|---|---|---|---|
| ガロン | 27 | 29 | +2 |
| ビクター | 28 | 30 | +2 |
| ザベル | 20 | 22 | +2 |
| モリガン | 25 | 27 | +2 |
| アナカリス | 25 | 27 | +2 |
| ビシャモン | 21 | 23 | +2 |
| サスカッチ | 21 | 23 | +2 |
| リリス | 25 | 27 | +2 |
| **デミトリ** | **31** | **26 / 28** | **成立しない(§4.6)** |

**その場起き上がりは `終端 $1a7 = anim44 のセル長合計 + 2`。8/8 で厳密に成立。**
+2 は `$07 == 0` でその場/移動を選んでいる 2 ティック分。

移動起き上がりは単一の法則にならない。アニメ 0x45/0x47 の途中で `$07` が
切り替わり、`$a` の符号で 0x46 と 0x48 に分かれ、しかも半数のキャラは
独自ハンドラを持つ。**こちらは実測値を持つ。**

## 5.5 ガード硬直

**ブロックは `$140` に独自の値を持ち、独自のクロックを持つ。** ROM 0x02393A:

```
02393A: 1D7C 0012 0140  move.b #$12, ($140,A6)   ; 空中ガード
023952: 700E            moveq  #$e, D0
023954: 4A2E 0038       tst.b  ($38,A6)
023958: 662A            bne    $23984            ; 空中なら分岐
02395A: 1D7C 0002 0140  move.b #$2,  ($140,A6)   ; ★ 地上ガード
023960: 1D7C 000E 0158  move.b #$e,  ($158,A6)   ; ★ ブロック硬直 14 ティック
023966: 1D7C 000E 01AB  move.b #$e,  ($1ab,A6)
02396C: 4A2E 03B4       tst.b  ($3b4,A6)
02397A: 700C            moveq  #$c, D0           ; アニメ 0x0C 立ちガード
02397C: 4A2E 0121       tst.b  ($121,A6)
023982: 700D            moveq  #$d, D0           ; アニメ 0x0D しゃがみガード
```

`$158` は 0x022492 で毎ティック −1(`$174` と同じ汎用タイマ更新ブロック)。
キャラ側のコードが**ガードキャンセルの可否をこれで判定している**
(0x02E17C / 0x02FFE2 が `$158` を見てから `$106` に技 ID を書く)ので、
**`$158` がブロック硬直の時計である**ことは疑いない。

| `$140` | 意味 |
|---|---|
| 0x00 | やられ |
| **0x02** | **地上ガード** |
| 0x04 | 空中やられ |
| 0x0A | ダウン起き上がり |
| 0x0E | 投げ |
| **0x12** | **空中ガード** |

**free-1 のシグネチャはガードでも同じ。** アーカイブに既にあった
**39 スパン全てで** `free-1` が `$05=02 / $06=04 / $07=00 / $140=02`、
`free+0` が `$05=00 / $06=00` だった(**39/39**)。

**つまりボタンを置く仕組みはそのまま使える。**ツールがガード硬直に入れなかった
唯一の理由は、シグネチャフックの `$140` 許可リストに 0x02 と 0x12 が
無かったことである(v143 で追加)。

### 5.5.1 `$158` はブロック硬直の長さではない

**`$158` はガードキャンセルの受付窓であって、free までの距離ではない。**
実測 118 スパンのうち **114 で free−1 の時点で既に 0** だった。

`$158` が非0 でなくなってから free−1 までの距離:

| 距離 | スパン | ヒットからの総復帰 |
|---|---|---|
| 10 ティック | 73 | 24 |
| 15 ティック | 28 | 29 |
| 19 ティック | 8 | 33 |

**ブロック復帰は 24 / 29 / 33 の3種**であり、`$158` は常に 14 の定数
(0x023960)なので、残りはブロックアニメ(0x0C 立ち / 0x0D しゃがみ /
0x0E 空中)の長さから来ているはずである。分割の鍵は未確定
(`$121` 立ち/しゃがみか、`$54` 技の強さか)。

**これが「ヒットでは必殺技が出るのにガードでは出ない」の正体だった。**
v143 は `$158 <= 8` で arm しており、それは free の **18 / 23 / 27 ティック前**。
認識器はステップを 14〜19 ティックで落とす(§3.3)ので、**モーションは毎回
期限切れになっていた。**

### 5.5.2 残りの長さは `$59` だけで決まる

実測 108 スパン、`$158` が 0 になってから free−1 までの距離:

| `$59` | 意味 | 距離 | 内訳 |
|---|---|---|---|
| 0 | 弱 | **10** | 31/31 |
| 1 | 中 | **15** | 26/31(残り 5 は 13) |
| 2 | 強 | **19** | 51/51 |

**立ち/しゃがみ(`$121`)は関係ない。**
v146 は小さいサンプルでたまたま相関していた `$121` を鍵に入れ、
強・立ちを 11 と誤った。待ち 0 では余裕が 19 ティックになり、
認識器のステップタイムアウト(14〜19)で毎回期限切れ —
「単発しゃがみ強は出るが立ち強はほぼ出ない」の正体である。
しゃがみ強は待ち 7 で余裕 12 になっていたので出ていた。**同じ法則の数字違い。**

v147 は待ちを `$59` だけで選ぶ(0 / 4 / 8)。どの系統でも余裕 11 前後になる。

### 5.5.4 連続ガードには原理的な限界がある

使える余裕は約 11 ティック(§5.5.2)で、ガードヒット 1 発は free を
**24〜33 ティック先へ押し出す**。つまり**次のヒットがモーション投入中に来る
文字列は、どうスケジュールしても置ききれない。**

v148 で「何ヒット目に狙うか」を設定にしたが、**ユーザの判断で撤去した**
(チートで多段の状況を作れるため)。ティック単位のエッジ計数と、
free のフレームを越えて生き残る必要のある抑止フラグという
実装コストに見合わなかった。`git show v149` に残っている。

現状はガードヒットごとに再 arm する。単発と緩い文字列がその対象である。

### 5.5.4.1 ただしこれは「入力経路の」限界である

**限界の正体はコマンドの受付窓であって、タイミング機構ではない。**
認識器はステップを 14〜19 ティックで落とし(§3.3)、ガードヒット 1 発が
free を 24〜33 ティック先へ押し出すので、文字列が続くたびにモーションが
期限切れになる。**入れるコマンドがあることが原因である。**

**Character Specific にはその窓が無い。**技 ID をメモリに書くだけなので、
文字列がどれだけ続いても撃つティックさえ合っていれば出る。
v165 バッチのブロックからの実測:

| ガードヒット数 | 結果 |
|---|---|
| 単発 | **23/23** |
| 2 発 | **4/4** |
| 5 発 | 4/6 |

いずれも `$06` = 0x0E の free+0、つまり真のリバーサルである。

**したがって密な連続ガードを練習するなら Character Specific を使う。**
入力経路で同じことをするには、文字列の長さを人間が教えてやるしかない
(v148 の「何ヒット目」設定。`git show v149` に残っている)。

### 5.5.5 ガードの前置きはフレーム経路のままにしてある

v150 でこれを起き上がりと同じティック駆動に移したが、**悪化した**
(28/59、v149 は 37/59)。v151 で最後のエントリを保持するよう直したが
それでも v147 の水準に戻らず、**v152 で v147 の実装に差し戻した**。

差し戻した実装:

* arm は `$158` のゼロエッジ + `$59` 別の待ち(§5.5.2)
* 前置きは `process_pending_input_sequence` がフレームごとに入れ、
  `hold_last` が最後の方向を保持する
* ボタンは free−1 のシグネチャが置く
* `blk_hold` により `release_input_sequence` は受け付けない

v150 で分かったことは記録しておく価値がある:
**マッチャは毎ティック `$12a` を比較する**ので

```
029F76: cmp.w D1, D0
029F78: bne   $2a57a   -> clr.b (A4)
```

**レバーが中立のティックは不一致となり進行が消える。**
起き上がりはエントリが free−1 まで連続しているので隙間が無いが、
ブロックは約 10 ティック手前で arm するため、**保持を欠くと途中で消える。**
`hold_last` はそのためにある。

### 5.5.3 多段ガードで昇龍拳に化ける

`hs_armed` は**スタン区間**で latch していたが、多段のガード硬直は
ヒットの合間に一瞬スタンを抜けることがある。そこで再 arm すると、
**まだ前のモーションを保持している認識器に 2 本目が入る。**

**QCF QCF の末尾は 前・下・下前 = 昇龍拳**である。
ユーザ報告「多段の場合は前のコマンドの残りと合わさってシャドウブレードに化ける」
の正体はこれ。v146 は `$140` が 0x02/0x12 でなくなるまで latch した。
ところがそれは**多段には強すぎた**: ヒットの合間に `$158` がたまたま 0 に
達するとそこでモーションが入り、次のヒットが free を 24〜33 ティック先へ
押し出すのに、再 arm されない。モーションは期限切れになり、
**文字列が終わったときには何も残っていない**(「多段ガードは全くダメ」)。

v147 は **`$158` が 14 に戻る立ち上がり = 新しいガードヒットごとに再 arm** する。
これで二重にはならない — 次の arm はゼロエッジ + 待ちなので**前の arm から
最低 22 ティック後**であり、認識器はステップを 14〜19 で落とすので
前のモーションは必ず消えている。

## 6. スタンとマッシュ

```
0260C0: 0200 000F       andi.b #$f, D0            ; 方向が入っているか
0260C6: 4EB9 0001 4E8A  jsr    $14e8a.l           ; 乱数
0260D0: 43FA 22F2       lea    ($283c4,PC), A1

0260F2: 43FA 2310       lea    ($28404,PC), A1
0260FA: 916E 015C       sub.w  D0, ($15c,A6)      ; ボタンで短縮
```

## ★ 最重要の規則 ★

> **必殺技コマンドで出すもの以外は、すべて free+0。**

**押しが free+0 に乗らなければ出ない。**遅れて出るのではなく、**出ない。**

| 種類 | 押す位置 |
|---|---|
| 必殺技コマンド(QCF / QCB / DPF / DPB / HCF / HCB / 360 / 720 …) | **free-1** |
| **それ以外すべて**(ダッシュ、ダッシュ中断、通常技、投げ、ジャンプ、DF) | **free+0** |

実測(v206、サスカッチのダッシュ中断)。タップが 1 ティック遅れただけの結果:

```
free+0  lev=.  (中立)
free+1  lev=2  (2 回目のタップ)
free+2  $06=04          <- 0x14 にならない。ダッシュが存在しない
free+4  btn -> $06=0A   <- ただの通常技が出る
```

### この規則から出る設計上の帰結

**free-1 シグネチャを起点にプレフィックスを配ってはいけない。**
シグネチャは free-1 なので、そこから 1 エントリ 1 ティックで配ると
**最後のエントリは必ず free+1 以降**になる。**引き取った時点で
非必殺技は死ぬ。**

* プレフィックスはフレーム側(アームから歩き始める)に任せる。
* したがって**シーケンスを長くしてはいけない。**配送が間に合わなくなり、
  最後のエントリが free+0 からずれる。
* 追加の入力が要るなら**シーケンスに足すのではなく、ティックフックが
  free+0 より後ろで持つ**(ダッシュ中断の逆方向がこの形)。

v203〜v207 はこの規則を知らずに 5 回作り直した。**新しい入力を足したく
なったら、まずこの表を見ること。**

### 8.3 テーブルに無いキャラが失敗する条件

`$21` フォールバックの arm が `$1a7` < 23 に落ちるキャラは、
pre-buffer をこの分岐にフラッシュされて消える。

| キャラ | 終端 | `$21` arm | 結果(v135 時点) |
|---|---|---|---|
| レイレイ | 29 | 約 20 | **0/33** |

| フェリシア | 55 | 約 49 | 9/9 |

(`kd_owned`)。どのクロックで駆動するかではなく**誰が arm したか**で判定する。

### 8.5 押した瞬間と行動の関係 ― 全アーカイブ 373 スパン

**押したエッジがティック X なら、行動はティック X+1 に始まる。例外なし。**

| 押した位置 | 行動の位置 | 件数 |
|---|---|---|
| free−1 | free+0 | 336 |
| free+0 | free+1 | 5 |
| free+1 | free+2 | 2 |
| free+2 | free+3 | 6 |
| free+3 | free+4 | 6 |
| free+4 | free+5 | 4 |

そして **free のティックに出せるのは必殺技(とガード)だけ**である。
通常技・ダッシュ・ダークフォース・ジャンプはそこでは拒否され、**次のティックから**。

この2つを合わせると:

| 出したいもの | 最速の出現 | 押すべきティック |
|---|---|---|
| 必殺技 / ES / EX | free+0 | **free−1 + ディレイ** |
| 通常技 / 投げ / ダッシュ / DF / ジャンプ | free+1 | **free+0 + ディレイ** |

**必殺技以外を free−1 に押すのは、出られないティックに要求している**ことになる。
v138 で分岐した。

判定は**必殺技コマンドの明示リスト**で行う。`SEQ_LEN` は使えない —
あれは「エントリ数」の表で `down-forward` も `forward dash` も載っているので、
しゃがみパンチを必殺技と判定してしまう(v139 で修正)。
ダッシュも意図的に外してある。コマンドではあるが、ゲームは free のティックでは
通常技と一緒に拒否するので遅らせる側が正しい。

**ダッシュは前置きの方向を先入れしてはいけない。**
ダッシュの最後のエントリは**方向の押し込みそのもの**で、ボタンが無い。
`$126` は `~$124 & $122` なので、前のティックから前が入っていると
**エッジが立たず 2 回目のタップが認識されない**。
先入れするのは「後ろにボタンが続くとき」だけにする(v140 で修正)。

**ガードアクションディレイはティックで当てる。**
従来は空エントリを先頭に足していたが、ティック駆動では
**モーション全体が前にずれるだけでボタンの位置は変わらない**ので効かなかった。
押す位置に対するオフセット(1 単位 = 1 ティック)として当てる。
前置きのモーションは動かさない — 認識器は完成したモーションを 14〜19 ティック
保持する(§3.3)ので、10 ティック程度の遅延なら拾える。
手で遅らせるリバーサルと同じ形である(v140)。

**旧経路の `inject_mask` を残すと通常技が二回出る。**
`inject_mask` / `inject_dir` は 0xFF8B94 の書き込みフックが**セットされている間
毎回の書き込みに OR し続ける**ワンショットである。必殺技では本来の押しと同じ
ティックに重なるので見えないが(同じ入力なので)、**通常技では別のエッジになる**。
VSAV は同じボタンの再入力で通常技を連打キャンセルするので、**2 回振る**。
ティックフックが持っているモーションではこれを立てない(v141)。

**単発エントリもホールドする必要がある。**素の通常技は 1 エントリで、
`queue_input_sequence` が「前置きが無いなら保持しない」としていたため
ティック経路に入らず、押す瞬間がフレーム境界任せになっていた。
ログでは `arm_result val=1 pc=0`(= シーケンスはあるが `hold_last` = 0)、
`press_defer` も `kd_step` も一つも出ない、という形で出る(v139 で修正)。

free のティックの識別は、いまは free−1 シグネチャの `lg`(0xFF8081)を控えて
差が 1 のティックを見ている。ROM 上は `$174` が使えるはずで
(`024F12` で 5 を書き `02247E` で毎ティック −1)、`$05 == 0 かつ $174 >= 4` なら
Lua 側の状態を持たずに済む。トレースに `w174` を載せたので次のバッチで確定する。

### 8.4 最速判定(FASTEST)

ゲームは REVERSAL を自分で出すが、**free の最初のフレームに出た必殺技だけ**である。
通常技・投げ・ジャンプ・ダッシュが同じフレームに出ても同じく完璧なのに何も出ない。

判定は `classify_reversals.py` と同じもので厳密:
**`$05` が 0x02 → 0x00 になったティックの `$06` が行動値なら、その行動はそのティックに始まった。**
0x00 のままなら、行動値になるまでのティック数がそのまま**遅れフレーム数**である。

1 ゲームティック = 1 ゲームフレーム。arm 側が気にしている
「1 表示フレーム = 約 1.6 ティック」は Lua のコールバック頻度であって
ゲームの進行ではない。

保存済み 148 スパンで再生し、**リバーサル判定と 144/144 で一致、不一致 0**。

**投げは表示されなかった**(v153 で修正)。理由は2つ重なっていた。

1. **`$05` が 0 でなくなった時点で諦めていた。** 投げは始まった同じティックに
   マスタ状態が 0x00 を離れるので、`$06` を見る前に数えるのをやめていた。
   本当に中断なのは **`$05` 非0 かつ `$06` == 0x00**(殴られたときの
   インパクトフリーズ)だけである。
2. **`$06` の表に載っていない値は行動として扱っていなかった。**
   ROM から網羅するのは安くない — `move.b #imm, ($6,A6)` はプログラム全体で
   10 箇所しかなく、残りは `addq` と `move.l` の一括書き込みを通る。
   そこで**未知の値は `ACT xx` として番号ごと表示し、ログに (`$05`,`$06`) を
   残す**ようにした。名前は次のバッチで付けられる。

**ただし「最速」はカテゴリで違う**(§8.5)。必殺技は free+0、それ以外は free+1 が最速。
表に無い行動は free+1 を最速として扱う(投げはコマンド通常技なのでそれで正しい)。

**行動でない値は 0x00 / 0x04 / 0x0C。** 0x0C はガードで、
ダミーが後ろを握り続けているだけなので計測対象ではない。

### 8.6 押しっぱなしの方向は再入力できない

ダミーはガードのため**後ろを押しっぱなし**にしている。トレースでは
`$394` の bit0 が 14 ティック以上連続で立っている。

`$126` は `~$124 & $122` なので、**既に握っている方向をもう一度要求しても
エッジは立たない。**バックダッシュの2回目のタップが存在しなかった理由がこれで、
前ダッシュが無事だったのは前が握られていないからである。

したがって**ボタンを持たないモーション**(ダッシュなど)は、
最後の押しの**1ティック前に中立を入れて離す**必要がある。
ブロック硬直中なのでその1ティックにガードが切れても殴られることはない。
手でバックダッシュを仕込むときに一度離すのと同じ動作である(v155)。

### 8.7 ダッシュの2タップは隣接していなければならない

v155 でエッジは立つようになった(`$126` = 0x0001 を確認)が、それでも出ない。
`hook_seq` が終始 102 を返しており、**タップは 2 回とも入っている** —
1 回目はキュー時、2 回目は free。**つまり 7〜8 ティック離れている。**

方向コマンドは認識器がステップを 14〜19 ティック保持する(§3.3)ので
離れていても繋がるが、**ダッシュは同じ方向の 2 度押しでダブルタップとして
読まれる**ため窓がずっと短い。

v156 は**ボタンを持たないモーション**に限り、1 回目のタップを押しの
2 ティック前に置く。ブロックの日程は arm の約 11 ティック後が free なので
(§5.5.2)、arm + 9 が free−2 にあたる。v155 が free−1 に中立、
free+0 に押しを置くので、**タップ・離す・タップが3連続ティック**になる。

必殺技には決して届かないよう「最後のエントリにボタンが無い」ときだけに
限定してある。v150 が全部を動かして失敗した反省である。

**そして1回目のタップの前にも中立が要る**(v157)。
既に方向を握っていれば1回目もエッジにならず、ゲームからは1回の長押しに見える。
ダミーはガードのため後ろを握っているので、バックダッシュでは常にこの状態。

実測(v156 バッチ)がはっきり示している:

| レバー | free+1 の `$06` | 件数 |
|---|---|---|
| −2:後ろ、+0:後ろ | **0x14 ダッシュ** | 14 |
| −3:後ろ、+0:後ろ | **0x14 ダッシュ** | 8 |
| −1:後ろ のみ | 0x00 | 7 |

**2タップが揃った 22 本は 22 本ともダッシュになっている。**
失敗は全て1回目が欠けたもの。したがって必要なのは

**中立 → 後ろ → 中立 → 後ろ の4ティック。**

そして**2回目の後ろは2ティック必要**(v158、実プレイからの報告)。
ボタンは押されたエッジが取られるティックだけ存在すれば良いが、
**ダッシュの2回目のタップはそうではない。**

したがって最終形は

| ティック | 入力 |
|---|---|
| free−3 | 中立 |
| free−2 | 後ろ |
| free−1 | 中立 |
| free+0 | **後ろ** |
| free+1 | **後ろ**(継続) |

保持を伸ばすのは**エントリがボタンを持たないときだけ**である。
必殺技や通常技は 1 ティックのままでなければならない —
それが連打キャンセルの二度振りを止めている条件だからである(§10)。

**そして位置は定数ではなく「余裕」から決めること**(v159)。
arm から free までの距離は `$59` 別に

| `$59` | 距離 | 待ち | **arm から free** |
|---|---|---|---|
| 0 弱 | 10 | 0 | **10** |
| 1 中 | 15 | 4 | **11** |
| 2 強 | 19 | 8 | **11** |

**弱だけ 1 ティック短い。**距離が既に窓の内側なので待つものが無いためである。

修正の効果(バックダッシュ、ガード硬直から):

| 版 | 単発 | 多段 |
|---|---|---|
| v154 | 5/65 | 0/6 |
| v158(2 ティック保持) | 12/26 | — |
| **v159(余裕基準)** | **32/37** | 16/29 |

v159 の単発内訳は **弱 12/12、中 16/20、強 2/2**。
固定オフセットで一番割を食っていた弱がそのまま埋まった。
v156/v157 は arm+8 と arm+9 に固定していたので、余裕 11 なら free−3 と free−2
だが、**余裕 10 では free−2 と free−1** になり、2 回目のタップ前の中立と
衝突してダッシュから間隔が消える。
「弱だと出にくい、たまに出る」がこれだった。
表示はカテゴリごとの下限を引いてから `+NF` を出す。
通常技が free+1 に出たときに `+1F` と出すのは、正しくやったのを咎めることになる。

### 8.2 入力履歴の表示

**問題は2つ重なっていた。**

**画面には入力表示が2つある。取り違えないこと。**

| 表示 | ファイル | 位置 | 対象 | 入力元 |
|---|---|---|---|---|
| 下部の帯 | `inputHistory.lua` | 画面下 | **P1(人間)** | メモリ `$122`/`$125`、表示フレームに1回 |
| 右上の縦列 | `vsavscriptv2.lua` | 右上 | **P2(ダミー)** | v134 まで `joypad.getdown(2)`、v135 からメモリを毎ティック |

**(1) ダミー側の履歴はそもそも描画されていなかった。**
`inputHistory.lua` の `input_history[2]` はファイルが書かれた時から維持されているが、
唯一の描画呼び出しが `input_history[1]` を渡していた。[1] に入るのは `"P1"` = 0xFF8400、
つまり**人間の入力**である。v134 で下段に足したが**画面が狭くなるので撤回した**。

ダミーを見るのは**右上の縦列**(`vsavscriptv2.lua` の scrolling input)である。
こちらは `joypad.getdown(2)` を読んでいた。**v131 以降ツールは `joypad.set` を使わず
`$394` へ直接書くので、パッドには何も映らない。**
v135 でメモリ由来に切り替えた。

**(2) 1 ティックしかない入力はフレームのサンプルの隙間に落ちる。**
`read_game_input` は `$122`/`$125` を**表示フレームに 1 回**読む。
v130 まで joypad.set が 1 エントリを 1 フレーム保持していたので問題にならなかったが、
v131 でモーションがティック単位になった。
v133 でティックフックから採取してフレーム側が排出する形にした。

採取は **`$123`** を使う(フレーム読みの `$125` ではない)。
`$125` は `$124` の下位 = **前ティック**の方向で、`$122` 上位の**今ティック**の
ボタンと組ませるとリバーサルのボタンが 1 つ前の方向に付く。
`$122`/`$123` は 0x02211A の 1 命令で同時に書かれる 1 語なので整合する。
フレーム読みが `$125` を選んでいるのは人間が方向を握っているときの
ちらつき対策(20.3% 対 4.2%)で、何も握っていないダミーには当てはまらない。

### 8.8 Character Specific も同じ時計に載せる

**これで入力で出す場合と 1 ティックも違わない。**
メモリ書き込みで技を出すモードと、コマンドを入力するモードが、
同じ arm と同じ配置ティックを共有している。

このモードは `$106` に技 ID を直接書く。従来は `guardCancelCheck`
(表示フレームに 1 回)から撃っており、**free に対してどこに落ちるか制御できて
いなかった** — v131 以前の入力経路と同じ問題である。

さらに悪いことに、可否の判定が `$06` だけを見ていた:

```lua
local action_slot = memory.readbyte(0xFF8806)
if action_slot ~= 0x00 and action_slot ~= 0x04 then return end
```

**`$06` == 0x00 は「待機」だけでなく、殴られたときのインパクトフリーズでもある。**
だから**くらいモーションの最中に必殺技が出て暴れる**ことがあった。
`$06` だけでは区別できず、`$05` を見れば区別できる。

v160:

* `$05` == 0x00(本当に自由)か、**free−1 シグネチャ**(02/04/00)のときだけ許可
* フレーム側は要求を立てるだけにし、**ティックフックが free−1 に撃つ**
* 要求はスタン区間の終わりで捨てる(後の別の回復で暴発しないように)

**そして要求を出す条件も入力経路と同じにする**(v165)。

v160 は要求を `should_reversal` で出していた。これは `0xFF8974`
(ゲーム自身のリバーサル窓)の立ち上がりを見る**反応型**で、
**窓が開くのは free のフレームかそれ以降**である。撃つ場所は free−1 なので、
**要求は常に 1 ティック手遅れ**だった。地上くらいが全く出ず、
ダウンと空中復帰が出たり出なかったりだったのはこれである
(フレームの揺れでたまたま噛み合った回だけ出ていた)。

`arm_edge` / `hs_arm_edge` / `BLK.edge` は `service_held_reversal` が
**入力経路のために計算している arm** であり、この文書の測定は全てそれに
対して行われている。Character Specific もそれで arm するようにした。
カウンター機能は `BLK.edge`(ブロックの時計、§5.5.2)で撃つ。

シグネチャを持たないキャラ(§4.7)は free のティックに撃つ。

### 8.10 単位は全てティック

**画面にもメニューにも「フレーム」とは書かない。**
1 表示フレームは約 1.6 ゲームティック(§0)なので、
このツールが測る・置く・待つ量をフレームと呼ぶのは端的に嘘である。

| 項目 | 単位 | |
|---|---|---|
| Guard action delay | ティック | v140 |
| GC input delay | ティック | **v167**(それまで表示フレーム) |
| 最速判定の表示 | `+N TICK` | **v167**(それまで `+NF`) |

表記は **`Tick`**(Title Case)で統一する。メニューの他の項目に合わせるため。

### 8.11 プッシュブロックの実体

**12 ティックの窓の中で何回押したかを数える仕様。**6 回で 100%。

```
023960: 1D7C 000E 0158  move.b #$e, ($158,A6)   ; ブロック硬直
023966: 1D7C 000E 01AB  move.b #$e, ($1ab,A6)   ; PB の受付窓 (同時に張られる)
02249C: 532E 01AB       subq.b #1, ($1ab,A6)    ; 毎ティック 1 減る (非 0 のとき)

0275D8: 4A2E 01AB       tst.b  ($1ab,A6)
0275DC: 6700 008A       beq    $27668           ; 窓が閉じたら PB は出ない
0275FE: 6100 FEBA       bsr    $274ba           ; $126 & $77 = このティックの押し
027602: 6764            beq    $27668           ; 押していなければ数えない
027606: 522E 0170       addq.b #1, ($170,A6)    ; 押した回数
02760E: 0C00 0008       cmpi.b #$8, D0
027612: 6418            bcc    $2762c           ; 8 回以上は無条件で成立
027616: 41FA 1738       lea    ($28d50,PC), A0  ; 8 未満は回数別の確率表
02761E: 4EB9 0001 4E8A  jsr    $14e8a.l         ; 乱数
027628: 0102            btst   D0, D2
```

`$1ab` はカウンタとしては 14 だが、両端のティックが使えないので**実際に押せる
のは 12 ティック**。`$274ba` が見ているのは `$126`(押した瞬間のバイト)を
`$77` でマスクしたもの、つまり**6 ボタンのどれでもよく、1 ティックにつき 1 回**。

**0x28D50 の中身は mame_code から読めない。**CPS2 は命令空間しか復号されない
ので、DATA テーブルは listing 上ではゴミになる(§0 参照)。実際 listing の
バイトを数えるとビット数が 18/19/16/13/… と回数に対して単調ですらなく、
明らかに読めていない。`debugKnockdown.lua` の `pb_prob_028D50` で実機から
ダンプするようにした(v170)。**回数ごとの確率は未測定。**

**間違えた解釈(記録として残す):**「入力の回数であって時間ではない」と書いたが
誤り。**回数と時間の両方**で、12 ティックという窓の中の回数を数えている。
メニューの元の説明「12 frames e.g. (lp, no input) x 6」はその窓と 6 回を
指していて、**もともと正しかった**。ツールのシーケンス長のことだと読み違えた。

**入力の出し方はティックでもフレームでもない。**PB のシーケンスは
`{LP},{},{LP},…` の 11 エントリで、`hold_last` を付けずに queue されるため
`process_pending_input_sequence` が**表示フレームに 1 つずつ**出す。
1 表示フレーム ≒ 1.6 ティックなので 11 エントリで約 18 ティックかかり、
**12 ティックの窓を大きく超える。**窓の中に入るのは 8-9 エントリ、つまり
**押しは 4-5 回にしかならず、6 回に届かない。**
ティック単位で出せば 11 エントリが 11 ティックに収まり、6 回全部が窓に入る。

**v184 で修正した。**`process_pending_input_sequence` は `pb_tick` を早期
return し(`kd_tick` と同じ扱い)、`guardCancel.lua` のティックフックが
1 ティックに 1 エントリ出す。タグ付けは共通の queue 地点(どの guard action が
作ったシーケンスか分かる唯一の場所)で行う。

押しは 1 ティックで足りる。ボタンはエッジが取られるティックに存在すれば
よく、2 ティック保持が要るのは**ボタンの無い**エントリ(ダッシュのタップ)
だけ。

ディレイの空エントリも 1 個 = 1 ティックになるので、メニューの「Ticks」
表記と一致する。

検証用に `$170`(押した回数)と `$1ab`(窓)をトレースに追加した
(`pbc` / `pbw`)。**`$1ab` が非 0 の間に `$170` がいくつまで行くか**が見たい値。

**実測(v184、窓エピソード 32 件):**

```
$1ab が非 0 の間に $170 が到達した値    6 回 : 32 件   (32/32)
1 回目から 6 回目までの所要             10 ティック : 31 件
1 回目が窓の何ティック目か              1: 14件  2: 10件  3: 7件
窓の長さ                                14 ティック : 28 件、13: 2、21/24: 各1
```

**32/32 で 6 回全部が窓に入った。**押しは 2 ティック間隔(タップ+空)で
5 間隔 = 10 ティック。1 回目が窓の 1〜3 ティック目なので、6 回目は
11〜13 ティック目 = 14 ティックの窓の中。設計どおり。

長い窓(21/24)はブロック持続で `$1ab` が張り直されたもの。

**ディレイを入れると外れる。**1 回目が既に窓の 3 ティック目まで遅れることが
あり、そこから 10 ティックで 13。余裕は 1 ティックしかない。
Guard Action Delay を上げると 6 回目から順に窓の外へ落ちる。

### 8.12 フレームトラップ表示(Tick Gap)

`globals.frames_between_attacks` は `playerObject.lua` で `emu.framecount()` の
差として取っていた。**表示フレームは約 1.6 ティック**なので、3 ティックの隙も
4 ティックの隙も同じ「2」と出ていた。**これは嘘の数字だった。**

見ていた辺は `$8805 == 2`(P2 がやられ/ブロック硬直)で、これは単なるメモリ
読みなのでティックフックでそのまま取れる。v169 で `guardCancel.lua` の
0x02211A フックに移し、`0xFF8081` の差でティック数を積むようにした。
表示も `Frame Gap` -> `Tick Gap`。20 以上は隙ではなく次の攻防、という元の
足切りはそのまま残してある。

**ダッシュ系の 4 つ(Dashes Interval / Dash Time / Dash Attack Cancel /
Attack Dash Gap)はまだ `emu.framecount()` のまま**で、表示フレーム数を出して
いる。辺の検出をティックに移さないと単位は直せない(表示フレーム差を 1.6 倍
しても実測にはならない)。メニューの説明に「DISPLAYED frames - not game Ticks」
と明記して、嘘にはならないようにした。**未変換。**

### 8.14 Guard Action Delay の意味 (v173)

**「最速でモーションを出し、その N ティック後にボタンを押す」**に変えた。

v172 まではディレイが**最後のエントリとボタンを一緒に**動かしていた。前置きの
プレフィックスは `$1a7` で置かれるので動かない。つまり
**Forward Dash + HP でディレイ 14** にすると:

```
free-3  tap1 (forward)      <- プレフィックス、動かない
free-2  neutral
free+14 tap2 (forward) + HP <- 最後のエントリ、ディレイぶん移動
```

**17 ティック離れていてダッシュにならない。**ただの遅い forward+HP。
必殺技が生き残っていたのは、コマンド認識のステップタイムアウトが 14-19
ティック (0x02A55A) で、たまたま隙間が収まっていたから。

v173 は 2 段に分けた。`fast_press_moff` が最後のモーションエントリ、
`fast_press_off` がボタン。ディレイ 0 なら同じティックで従来と同一。

```
free-3  tap1 (forward)
free-2  neutral
free-1  neutral
free+0  tap2 (forward)      <- モーションは最速のまま
free+1  (release or hold)
  ...
free+14 HP                  <- ボタンだけ待つ
```

待っている間のレバーは**必殺技以外は押しっぱなし**(v174)。

v173 はダッシュでレバーを離していた。「ダッシュはタップなのでエッジだけで
足りる」という理屈だが、それは**ダッシュを始める**話で、**続ける**話では
なかった。実測で **ディレイ 0-3 ではダッシュ攻撃が出て、4 で歩き攻撃に
なる**という報告。レバーを離すと走りが終わるので、4 ティック目にはキャンセル
するダッシュが残っていない。手でやるときに前を押しっぱなしにするのは
まさにこのため。

必殺技だけは離す。既に成立していて 14-19 ティック保持される (0x02A55A) ので、
最後の方向を握ったままだと歩くだけで、押しがコマンド技として読まれる危険が
増える。

**なお固定長のダッシュはそれでも終わる。**ダッシュ自身の長さを超えたら何を
握っていても歩き攻撃になる。これはキャラの仕様でツールの問題ではない。

**既知のリスク:** 待ち中は毎ティック early return するので、フック末尾の
BLK 記帳(`BLK.prev158` / `BLK.episode`)がその間走らない。従来も 1-2 ティック
は同じだったが、14 だと長い。ディレイ付き起き上がりリバーサルの最中に
ブロックが始まった場合だけ影響する。**未検証。**

### 8.15 ダッシュ攻撃が出ないのはディレイのせいではない (v174 実測)

v174 のログ 5 本(8 スパン)を `dash_delay.py` と手読みで確認した。
`$06 == 0x14` がダッシュ状態そのものなので、出たか出ないかは一目で分かる。

**成功したスパン**(g はティックカウンタ 0xFF8081):

```
g=142  $05=02 $06=02 lev=2               <- 1 回目のタップ
g=143  $05=02 $06=04 lev=.  press_defer  <- 中立(署名ティック)
g=144  $05=00 $06=00 lev=2  motion_now   <- 2 回目のタップ
g=145  $05=00 $06=14 lev=2  motion_now   <- ダッシュ成立
...
g=149  $06=14 lev=2 btn=04  press_now    <- HP、ダッシュ中に入っている
```

**失敗したスパン:**

```
g=109  $05=02 $06=02 lev=.               <- 1 回目のタップが無い
g=110  $05=02 $06=04 lev=.  press_defer
g=111  $05=00 $06=00 lev=2  motion_now
g=112  $05=00 $06=04 lev=2  motion_now   <- $06 は 04 のまま。ダッシュにならない
g=116  $06=04 lev=2 btn=04  press_now    <- 歩き + 通常技
```

**違いは 1 回目のタップの有無だけ。**失敗側では署名ティックの前に `lev=2` が
一度も無く、前方向は 2 回目のタップから押しっぱなしになるだけなので、
エッジが 1 回しか立たない = 歩き。

**ディレイとは対応していない。**成功したスパンの 1 つは
`press_now - motion_now = 5`(ディレイ 5)で、ダッシュ中に HP が入っている。
失敗側にもディレイ 5 と 6 が混ざっている。**同じディレイで出たり出なかったり
している。**

これらのログはどれも `$140` が 0x0A ではない、つまり**起き上がりではなく
やられ/ブロック復帰**。プレフィックスを置く `$1a7` の経路は
`memory.readbyte(0xFF8940) == 0x0A` で門番されているので、この経路では
1 回目のタップが出ない。出ていたスパンは別の経路(hs のフラッシュ)が
たまたま届けたもの。**要調査。**

### 8.16 地上くらいのプレフィックスをティックで出す (v176)

8.15 の原因。**やられ復帰(地上くらい)ではモーションをフレーム側が歩く。**
`process_pending_input_sequence` は表示フレームに 1 エントリなので、
アームのリードと競争になる。リードは `HS_LEAD_BY_59`、つまり**当たった技の
強さで変わる**ので、間に合ったり間に合わなかったりする。これが「同じディレイ
で出たり出なかったり」の正体。

起き上がりには v131 で `$1a7` のティック駆動を入れたが、その門番は
`memory.readbyte(0xFF8940) == 0x0A` で**起き上がり専用**。やられ復帰は
そこを通らない。

v176: 署名ティックの時点で**フレーム側が出し残したエントリを引き取り**、
ティックフックから 1 ティックに 1 つ出す。`controller.lua` は書いてから
`current_frame` を進めるので、その値が「次に出すエントリ」= 出し残しの先頭。

```
_moff = max(base, 出し残しの数)      -- 最後のエントリはその後ろ
_off  = _moff + delay                 -- ボタンはさらに後ろ
```

出し残しが 0 なら `_moff == base` で v174 と完全に同じ。ディレイ 0 でも
出し残しがあれば引き取る(門番を `moff < off` にすると既定値で素通りする)。

エントリはビットではなく**エントリのまま**保持する。`entry_to_bits()` は
呼んだ瞬間の向きバイトで forward/back を解決するので、注入時に変換しないと
振り向きで逆になる(`hs_request_flush` と同じ理由)。

### 8.17 current_frame は「入った」証拠にならない (v177)

v176 のログ(地上くらい、forward dash + HP、ディレイ 2/3/4/5)を読んだ結果。

**ディレイ 4 のスパンは `current_frame` が毎回 2**、つまりフレーム側は
エントリ 1 を送ったつもりでいる。ところが**半分は `$394` に forward が
14 ティック遡っても一度も現れない。**

```
成功 s10:  g=180 lev=2  -> g=183 で $06 = 0x14   ダッシュ
失敗 s09:  g=54..67 lev=. のみ -> $06 = 0x04     歩き
```

同じディレイ、同じキャラ、同じ設定。**カウンタは進むが入力は届いていない。**
これが「4 は乱れる」の正体で、`current_frame` を使った算術では直せない。

成功するときの forward は**必ず署名ティックの 1 つ前**に現れる。
`arm_edge` から署名までは 5〜8 ティックとばらつくので、フレーム側
(表示フレームに 1 エントリ)が最後の 1 つ前に間に合うかどうかの運になる。

v177: **モーション全体をティックフックが出す。**フレーム側の申告は無視。
既に入ったエントリを再送しても損はない - ティックフックはゲームが読む
コピーの直前に書くので、そのティックの最後の書き込みだけが効く。

```
sig+0  entry1 = forward   tap1
sig+1  entry2 = {}        中立
sig+2  entry3 = forward   tap2   -> free+2 でダッシュ
sig+2+delay  ボタン
```

**代償は 1 ティック。**理論上の最速(free+1)より 1 遅い。署名ティックが
free-1 なので、tap1 を free-2 に置くことは原理的にできない。

**kd_tick のシーケンスは対象外。**起き上がりは `$1a7` のスケジュールが
既に 1 ティック 1 エントリで前置きを歩いており、
`process_pending_input_sequence` は kd_tick を早期 return するので
`current_frame` が動かない。引き取ると**二重入力になる**(v176 の潜在バグ)。

### 8.18 ダッシュの 1 回目のタップは「位置」ではなく「有無」(v178 実測)

v176 のログ(地上くらい、forward dash + HP)で、**署名の前に最後にレバーが
入っていたティック**と、**`$06` が 0x14 になったか**を突き合わせた。

```
free-2 でタップ    ダッシュ x12       タップが一度も無い   ダッシュせず x8
free-3 でタップ    ダッシュ x3
free-4 でタップ    ダッシュ x3
free-10 でタップ   ダッシュ x1
```

**間隔は問題ではない。10 ティック前でも出る。**このバッチの失敗は全て
「1 回目のタップがそもそも入っていない」ケースだった。

これで 2 つの案が同時に死ぬ。

* **v177 の「署名からモーション全体を歩く」** — 署名は free-1 なので 1 回目を

### 8.19 ディレイが二重に効いていた (v179)

v178 の全掃引(ディレイ 2〜12、82 スパン)で**単調な落ち方**が出た。

```
delay 2  dash 6/7      delay 6   dash 0/6
delay 3  dash 23/30    delay 7   dash 0/5
delay 4  dash 7/15     delay 8+  dash 0/14
delay 5  dash 2/5
```

ダッシュが出たときの開始は 42 中 33 が署名+2 = **free+1、つまり最速**。
出るときは正しく最速で、出る確率だけがディレイとともに落ちていた。

原因は**ディレイの二重適用**。`make_input_sequence` の `delay_before` は
ディレイぶんの空エントリを**モーションの前に**挿入する。一方ティックフック
は `kd_press_offset()` で**押しにも**同じディレイを足す。起き上がりでは
`arm_edge and "" or delay_type` で前者を止めていたが、**やられ復帰は
止めていなかった**(コメントに「The hit-stun path still uses them」と
書いてあった。フレーム駆動だった頃の名残)。

結果、ディレイ N の forward dash はこうなる:

```
{} x N, {forward}, {}, {forward}
```

* `sequence[1]` が**空**になるので、v178 がアームで入れる「1 回目のタップ」は
  ニュートラルだった。**v178 はディレイ 1 以上で何もしていなかった。**
* フレーム側が forward に到達するまで N 個余計に歩く必要があり、
  **ディレイが大きいほどタップが間に合わない。**上の単調な落ち方そのもの。

v179: リバーサル/カウンターの経路は常に `"" , 0`。モーションは即座に入り、
待つのはボタンだけ。プッシュブロックと録画再生はフレーム側が配送を持って
いるので `delay_before` のまま。

### 8.25 `$170` が途中で止まるのは成功したから (v187)

v186 のバッチで `$170` の到達値が 2/3/4/5/6 とばらけ、v185 の 32/32 からの
後退に見えた。**ツールは全 11 エントリを出しており(`pb_tick` 1〜11、
奇数エントリで `btn=01`)、止まっているのはゲーム側のカウンタ。**

原因は `$184`:

```
0275E0: 4A2E 0184       tst.b ($184,A6)
0275E4: 6600 0082       bne   $27668      ; 非 0 ならルーチンごと拒否
...
027632: 1D7C 0001 0184  move.b #$1, ($184,A6)   ; プッシュブロック成立時
02762C: 1D7C 0010 0171  move.b #$10, ($171,A6)
```

**プッシュブロックが成立した瞬間に `$184` = 1 になり、以降の押しは数えられ
ない。**つまり `$170` が 3 で止まったのは「3 回しか入らなかった」ではなく
**「3 回目で成立した」**可能性がある。8 未満は確率表なので、3 回で当たる
ことは普通にある。

`$06`/`$140` では成功と失敗を分けられなかった(押しが数えられた例と
無視された例が両方に出る)。`$184` と `$171` をトレースに追加した
(`pbok` / `pbst`)。**これが無いと 2 つの場合が区別できない。**

**ヒットストップの長さで窓の中身が変わる。**押しが実際に数えられるのは
`$06 == 0` の間が主で、その長さは技によって変わる:

```
v185 バッチ  $06==0 が 11 ティック : 32 件中 24
v186 バッチ  $06==0 が 4〜7 ティック
```

同じボタンを使う `All Light/Medium/Heavy` は **タップ+空で 2 ティックに
1 回**。`Ascending`/`Descending` は 6 個の別ボタンを 6 エントリ連続で出すので
`$126 & $77` が毎ティック新しいビットを拾い、**6 ティックで 6 回**になる。

**ただし実測では同じボタンでも足りている(8.27)。**

### 8.26 ランダム再生スロットのクラッシュ (v188)

```
macro.lua:798: attempt to perform arithmetic on field 'num' (a nil value)
```

`get_playback_file(with_slot_num)` は通常 `{slot=, num=}` を返すが、
**有効なスロットが 1 つも無いときだけ文字列を返していた**。
`playcontrol()` はその戻り値に `slot.num + 1` をするので、文字列を

**再現条件: `Use Random Recording Slot` が ON で `Enable Slot 1〜5` が全部 OFF。**
このオプションの初期状態そのもの。録画再生を伴うガードアクション

3 点直した。

* 無効時の早期 return が `with_slot_num` の形に合わせて table を返す。
* `if with_slot_num == false` -> `if not with_slot_num`。呼び出し側は引数

* `playcontrol()` 側でも型を確認し、駄目なら通常の取得に落とす。

### 8.28 Counter 機能の現状 (v190 時点、未測定)

  `attack_frame - current_frame <= #sequence + 1` は 0 から大きなフレーム番号を

### 8.29 Counter をリバーサルのティック機構に載せた (v191)

**Counter = リバーサルから起き上がりのアームを外したもの。**それ以外に違いは
無い、というのが読み切った結論。

```
reversal :  arm_edge  or hs_arm_edge or BLK.edge     起き上がり / くらい / ガード
counter  :               hs_arm_edge or BLK.edge     くらい / ガード
```

なので分岐を統合し、アームの条件だけを分けた。free-1 署名、ティック駆動の
プレフィックス、`kd_press_offset()`、最後のエントリの保持 — **リバーサルで
測り込んだものが全部そのまま効く。**

撤去したもの:

* **`$164`(ガードの押し戻しタイマー)を見る発火条件。**これが「動ける瞬間」
  かどうかは一度も確認されていなかった。ブロック側は `$158` と `BLK_LEAD` で
  free を出しており、そちらは検証済み。
* **フレーム側での配送。**`process_pending_input_sequence` が表示フレームに
  1 エントリ歩く形で、リバーサルが v131 で捨てたもの。
* **`frameEndedGuarding`。**読者が消えた(8.28 参照)。

`Character Specific Counter` も `BLK.edge` だけだったので `hs_arm_edge` を
足した。**入力型の Counter と同じ 2 つの事象で armするようにした**(以前は
ガード後のみで、片方だけ狭かった)。

録画型の 2 つ(`Counter Attack - Recording` / `recording on counter`)は
`should_counter` のまま。マクロ再生はフレーム単位なので性質が違う。**未変換。**

**v191 の `hs_arm_edge` は広すぎた (v192 で修正)。**「起き上がり、空中やられ
にも出てしまう」という報告どおりで、hit stun の arm は **`$140` が区別する
3 種類の復帰を全部含む**:

```
$140 = 0x0A   起き上がり        -> カウンターではない
$140 = 0x04   空中やられ復帰    -> カウンターではない
それ以外      地上くらい        -> カウンター
```

`counter_arm_edge()` にまとめ、入力型と Character Specific の両方で使う。
`$140` はアームの瞬間に読む。行動可能ティックの直前で、復帰種別はとうに
決まっている。

**この補助関数は `BLK` と `hs_arm_edge` の宣言より後ろに置くこと。**前に
置くと本体の `BLK` がグローバル読みになり、`BLK.edge` が nil を索引して
落ちる(§10 の再発クラス)。

**v192 でもまだ全部出た。原因は 2 つあった (v193)。**

**(1) `$140` だけでは起き上がりを判別できない。**保存ログ全バッチで
`hs_arm` が実際に発火したティックを数えると:

```
$140=0A  $1a7>0    120     起き上がり(ラベルあり)
$140=00  $1a7>0     78     起き上がり(ラベル無し。$140 が 0)
$140=04            1297    空中やられ復帰
$140=00/02/0E  $1a7=0      地上くらい / ガード
```

**5 分の 1 の起き上がりが `$140` = 0 で来る。**`$1a7` は起き上がりの
カウンタで、起き上がり中しか進まない(KD_END_1A7 の前提そのもの)ので
そちらを先に見る。保存ログで再生して確認済み: v192 は 78 件通し、
v193 は 211 件全部止める。地上/ガード 3649 件は両方通す。

**(2) 本命はリバーサル分岐の「反応型フォールバック」。**
`should_reversal` は `0xFF8974`、**ゲーム自身のリバーサルウィンドウ**で、
これは起き上がりでも空中でも地上でもガードでも**等しく開く**。
アームが正しく拒否しても `prebuffer_used` が false のままなので、
この後段が結局モーションを queue していた。**門は正しく、その裏に
別の口が開いていた。**

カウンターは「どこで出てよいか」で定義される機能なので、それを判別できない
この経路はカウンターでは走らせない。`if should_reversal and not _is_counter`。
アームが取れなければ何も出ない、が正しい答え。

### 8.30 `a and b or c` で門が素通りしていた (v194)

v193 でもまだ全部出た。実測(v193 バッチ、`arm_result` を復帰種別で分類):

```
起き上がり   技が出た 9 / 出ない 0     <- 止まっていない
空中         技が出た 10 / 出ない 3    <- 止まっていない
ガード       技が出た 3 / 出ない 4
地上くらい   技が出た 0 / 出ない 5     <- 出るべきなのに出ない
```

**門は書けていたが、書き方が Lua の罠だった。**

```lua
local _armed = _is_counter and counter_arm_edge()
                or (arm_edge or hs_arm_edge or BLK.edge)
```

`a and b or c` は **b が偽になり得ないときしか成立しない**。ここでは
`counter_arm_edge()` が false を返すことこそが仕事なので、**拒否するたびに
`or` の右に落ちてリバーサルの条件で arm していた。**門を通した意味が無い。

```lua
if _is_counter then _armed = counter_arm_edge()
else                _armed = (arm_edge or hs_arm_edge or BLK.edge) end
```

**同種の式を全部見直した。**`fast_press_moff = _split and _moff or _off` など
3 か所は中身が数値で、**Lua では 0 も真**なので安全。false を返し得る
ブール関数を挟んだのはここだけだった。

`ctr_arm` マーカーを追加(val = `$140`<<8 | `$1a7`、pc = `$38`)。
次のバッチは推定ではなく記録から分類できる。

**地上くらいで出ない件も、壊れた門の副作用だった。**

### 8.31 Counter 決着 (v194 実測)

`ctr_arm` は記録された種別そのものなので、推定なしで分類できる。

```
ctr_arm が発火した復帰      ガード 10 / 地上くらい 21
                            起き上がり 0 / 空中 0      <- 門が効いている

技が出たか                  ガード      10 / 10
                            地上くらい  20 / 21
```

**合計 30 / 31。**起き上がりと空中では一度も arm していない。

v193 で「地上くらいだけ出ない」と見えたのは、壊れた門を通って**別の経路で
arm した個体**を数えていたため。門を直したら地上くらいが 20/21 になった。

これで Counter はリバーサルと同じティック機構の上で、**ガード後と地上くらい
後だけ**に発火する。録画型の 2 つ(`Counter Attack - Recording` /
`recording on counter`)だけが `should_counter` のまま残っている。

### 8.34 ダッシュ中断は「押しっぱなし」でよい (v201)

出典: 攻略 wiki サスカッチ、ショートダッシュ《SD》の節。**ターボ3 と明記**。

* ショートダッシュ(ダッシュ中断)は**ダッシュした 5F 後にレバーを逆方向**に
  入れると成立する。斜め下でも可。
* **認識するタイミングは 1F のみ。**
* **ダッシュした直後からレバー逆方向に入れっぱなしにして問題ない。**
* **レバー逆方向と同時に攻撃ボタンを押しても**ショートダッシュ攻撃になる。
* **バックダッシュのショートもまったく同じ。**

これで **per-character の `cancel_frame` は要らなくなる。**1F の窓は
**押しっぱなしなら外しようがない。**

v201: 逆方向をシーケンスの**最後のエントリ**に置き、そのまま保持する。

```
forward dash cancel : {forward},{},{forward},{back}
back dash cancel    : {back},{},{back},{forward}
```

ティックフックは**ボタンの無い最後のエントリを待ち中ずっと保持する**
(`kd_holds_direction`)ので、wiki の「入れっぱなし」そのものになる。
`_delay_num` で空を積む処理と、後ろに付けていた `{opposite}` + `{}` は撤去。

**`fc`/`bc` の意味が「逆方向からボタンまでの間隔」に確定した。**
wiki が「同時でもよい」と言っているので **0 は合法**。サスカッチの 0 は
**実測値**であって埋め草ではない。他キャラの 10 は旧ビルドの `cancel_frame`
= 別の意味の数値なので、**そちらが調整対象。**

### 8.35 Auto の数値調整は引き継ぎ (v202)

**`analysis/引き継ぎ_Autoダッシュ調整.md`** が渡す文書。

要点だけ再掲:

  あれは「逆方向をいつ入れるか」であって**別の意味の数値**。10 に根拠は無い。
* `bc` は未実測で `b` のコピー。
* デミトリ (0x01) は行が無く Auto が効かない。
* サスカッチの `fc`/`bc` = 0 と、モリガンの `f`/`b` = 12 は根拠あり。

**メニューで数字を直接探ってから表に書き写す**のが最短、と文書に書いてある。
`Auto` は表の値をメニューに入れるのと同じことをしているだけなので、探索を
コード側でやる理由が無い。

### 8.36 逆方向はダッシュが出来てから (v203)

v201 でサスカッチが**ダッシュ自体しなくなった。**

原因は押し→行動の 1 ティック則。**2 回目のタップがティック X なら
ダッシュは X+1 に立つ**ので、タップの次のエントリに置いた逆方向は
**ダッシュが生成されるまさにそのティック**に乗る。ゲームが見るときには
レバーが既に逆になっていて、**ダッシュが発生しない**。
発生しないものは中断もできない。

wiki の「ダッシュした直後から入れっぱなしで問題ない」は**人間の「直後」**、
つまりダッシュが見えてからの話で、**出るティックそのものではない。**

v203: ダッシュ方向を数ティック保持してから逆方向に倒し、そのまま保持する。

```
forward dash cancel : {forward},{},{forward},{forward},{forward},{back}
                                            ^^^^^^^^^^^^^^^^^^^^ 保持
```

`DASH_CANCEL_LEAD_TICKS = 2`(`controller.lua`)。**保持がある限り 1F の窓は
外しようがない**ので、このティック数は「窓に当てる」ためではなく
**ダッシュ自身に 1 ティック与える**ためのもの。名前を付けてあるので、
長さが要るキャラが出たらここを動かす。

### 8.37 長いモーションはフレーム側が歩ききれない (v204)

サスカッチの `Forward Dash Cancel` が**一度も出なかった。**

プレフィックスは通常 `process_pending_input_sequence` に任せており、これは
**表示フレームに 1 エントリ**。3 エントリのモーション(ダッシュ、QCF、DPF)
なら、アームから署名までの 5〜8 ティックで前の 2 つが入るので間に合う。
しかも**ティックフックが引き取るより 1 ティック速い** - 1 回目のタップが署名
より前に入るので、2 回目が free+0 に置ける(v178 はこれを守るために引き取りを
やめた)。

**長いモーションでは破綻する。**v203 でダッシュ中断は 6 エントリになり、
前の 5 つに約 7 ティック要る。リードはそこまで無いので**モーションが完成せず
何も出ない。**

v204 は**長さだけで判定して必殺技を壊した。**「360 / HCF / 720 も出ていな
かったはず」という推測は**誤り**で、あれらは問題なく出ていた。引き取ると
**押しが free-1 から free+3 以降に動く** - 必殺技の押しは `kd_press_base` が
0 を返す通り **free-1 が定位置**で、最後のエントリは前のプレフィックスが
出きるまで置けないため。**4 ティック遅い必殺技はリバーサルではない。**

v205: **必殺技は除外**し、長さで引き取るのは**必殺技でない 4 エントリ以上**
だけにした。該当するのは**ダッシュ中断のみ** - 実際に壊れていた唯一のもの。

```
motion            entries  special  prefix        press
forward dash      3        no       フレーム側    free+0
QCF/DPF           3        yes      フレーム側    free-1
360               4        yes      フレーム側    free-1
HCF/HCB           5        yes      フレーム側    free-1
dash cancel       6        no       ティックフック free+4
720               8        yes      フレーム側    free-1
```

**教訓。**「これも壊れていたはず」と広げるのは、直す話ではなく**壊す話**に
なりうる。報告されたのはダッシュ中断だけだった。

### 8.38 バックダッシュが出ない - 同じ罠が 2 か所目 (v206)

ブロック経路のダッシュ用スケジューリング(中立 -> タップ、v157)が
**`_lastbtn == 0` で門番されていた。**必殺技を除くつもりの条件だが、
`make_input_sequence` は**ボタンを最後のエントリの中に入れる**ので、
バックダッシュ + LK は `{back, LK}` になり**丸ごと素通り**していた。

**前ダッシュは出てバックダッシュだけ出ない**という非対称は、これで説明が付く。
ダミーはガードのため **back を押しっぱなし**なので、back を再度入れても
`$126` (= `~$124 & $122`) が立たず、**1 回目のタップが存在しない**。
前方向は握っていないので影響を受けない。

**v180 の `dash_pre` とまったく同じ間違いを、もう 1 か所でしていた。**
モーション名で判定するように変更(`is_plain_dash()`)。

中断は**意図的に対象外**にした。v204 以降プレフィックス全体をティックフックが
出しているので、ブロック経路が二重にタップを置くと壊れる。

### 8.39 ダッシュ中断の作り直し (v207)

**2 回目のタップが free+0 に落ちないとダッシュは出ない。**v206 のログが
決定的だった(サスカッチ、`forward dash cancel`):

```

free+0  lev=.  (中立)
```

限り構造的に 1 ティック遅れる** - つまり**引き取った時点でダッシュは死ぬ。**

v207: **ダッシュ中断のシーケンスを平ダッシュと同一の 3 エントリに戻した。**

サスカッチの `fc = 0` は「逆方向とボタンが同じティック」= wiki の

v204 の長さ判定と v205 の必殺技除外、v203 の `DASH_CANCEL_LEAD_TICKS` は
**全部不要になったので撤去。**唯一の長いモーションが中断で、それが 3 エントリ

### 8.40 中断もタップのスケジューリングが要る (v209)

**バックダッシュ中断が出ない。**

v206 で `is_plain_dash()` を作ったとき、**中断を意図的に除外**した。当時は
中断が独自のティック駆動プレフィックスを持っていたため。**v207 でそれを
撤去したのに、除外だけ残っていた。**

中断のシーケンスは v207 以降**平ダッシュと同一**で、違うのは後ろの逆方向だけ。
つまり**ダッシュ半分にはまったく同じ中立/タップのスケジューリングが要る。**
除外されていたので、バックダッシュ中断の 1 回目のタップに押しエッジが立たず
(ダミーはガードで back を握っている)、**何も出なかった。**
v206 の平バックダッシュとまったく同じ失敗を、1 つ先のモーションでしていた。

`PLAIN_DASH` に 4 種類全部を入れた。

**サスカッチの `fc` は 7**(利用者が本ビルドで実測)。旧ビルドの
「ボタンをキャンセルと同じフレーム」から 0 と読んだのは**このビルドでは誤り**
だった。`bc` は未実測のまま(中断自体が出ていなかったので測れなかった)。

### 8.41 タップ注入は「後ろ」だけ (v210)

**2 つの報告が同じ事実の裏表だった。**

**前方向は握っていない。**だから前ダッシュには元から不要で、**入れると
モーションが頼んでいないタップが 1 つ増える。**それで前が壊れていた。

### 8.42 押しエッジを作る解放を長くする (v211)

タップの前の解放は 1 ティックだった。**押しエッジを作るのがその 1 ティックの
仕事**で、短いと取りこぼす。`BACK_TAP_NEUTRAL_TICKS = 3` にした。

```
lead=10/11 とも   free-5, -4, -3 で解放   free-2 で 1 回目のタップ
                  free-1 は署名(中立)     free+0 で 2 回目のタップ
```

**ダッシュ側の代償は無い。**この区間はブロック硬直の中で、ダミーはどのみち
動けない。

**ブロック連係では無料ではない。**解放中はレバーが back から外れるので、その
ティックに来た攻撃はガードされない。**1 ティックだったときも同じ性質**で、
長くなっただけ。多段が抜けるようになったら下げる値。

### 8.43 強度で出方が違う (v212、調査中)

報告: バックダッシュは出るが**出ないこともあり、大攻撃のほうが出ない確率が
高く見える。**

**強度はブロックのリードそのもの。**`BLK_LEAD` は `$59` で引く表で
0(弱)=10 / 1(中)=11 / 2(強)=11。解放とタップは `_dlead` から逆算して
置いているので、**リードが強度ごとに 1〜2 ずれていれば、そのままずれる。**

v212 で 2 つ。

* 解放を 3 -> **5 ティック**に。リードが多少ずれても解放が届く。
  `free-7 .. free-3` を解放し、`free-2` で 1 回目のタップ。
* `dash_rel1` / `dash_tap1` の記録値を **`$59`<<8 | `_dlead`** にした
  (pc は `_dstep`)。**次のバッチを強度で分類できる。**

**これは調査であって修正ではない。**リードのずれが原因なら `BLK_LEAD` の値を
直すのが本筋で、それは実測が要る。

### 8.44 タップが署名ティックに乗ると死ぬ (v213 実測)

v212 のバッチ、1 回目のタップから実際の free までのティック数を強度別に:

```
$59=0 弱    3 x4   2 x3                1 は無い
$59=1 中    2 x8   3 x3   1 x2
$59=2 強    2 x8   3 x4   1 x3
```

**距離 1 = タップが署名ティック(free-1)に乗った。**このブロックは署名フック
より先に `return` するので、**free-1 に入るはずの中立が入らない。**すると
free+0 の 2 回目のタップにエッジが立たず、**ダッシュが出ない。**
頻度が 弱 0 / 中 2 / 強 3 で、報告(「弱は完璧、中はたまに、強はもっと」)と
**完全に一致する。**

**アームから free までの実距離は 1 ティック前後揺れる。**`BLK_LEAD` は強度
ごとに 1 つの数値なので追従できない。そこで**精度を上げるのではなく、
タップを太くする。**

```
BACK_TAP_NEUTRAL_TICKS = 4   解放(5 から 1 減らした)
BACK_TAP_HOLD_TICKS    = 2   タップを 2 ティック保持(1 から)
BACK_TAP_BIAS          = 3   さらに 1 ティック早く置く
```

**2 ティックのタップは 1 ティックより取られやすく、長く持っても損は無い。**
増やした 1 ティックは解放から出しているので**全体の長さは変えていない**
(ブロック連係でレバーが back から外れる時間が延びない)。

太くしたぶん free-1 に届きやすくなるので、置く位置を 1 早めた:

```
強度  lead  解放@_dstep   タップ@_dstep   最後のタップ->free(実距離 lead±2)
弱     10   1,2,3,4       5,6             2,3,4,5,6
中     11   2,3,4,5       6,7             2,3,4,5,6
強     11   2,3,4,5       6,7             2,3,4,5,6
```

**どの実距離でも 1 にならない。**早いのは無害(10 ティック前でも出る、8.18)、
遅いのだけが致命的、という非対称を使って**外れる向きを安全側に倒している。**

**実機で確認済み(2026-08-20):弱・中・強すべて安定。**
サスカッチの 4 方向(前/後ろ/前中断/後ろ中断)がすべて出る。
`f=2 b=1 fc=7 bc=7` は本ビルドでの実測値で、他キャラを詰めるときの基準。

**解放を広げる代償**は 8.42 と同じ - その間レバーが back から外れるので、
ブロック連係で抜けられる可能性が上がる。多段が抜けるようになったら
`BACK_TAP_NEUTRAL_TICKS` を下げる。

### 8.45 デミトリのダッシュは中断できない

攻略 wiki デミトリ、基本動作:

```
前ダッシュ   中断不可、終わり際をダッシュでキャンセル可能
後ダッシュ   中断不可、終わり際をダッシュでキャンセル可能
```

**`Forward Dash Cancel` / `Back Dash Cancel` はデミトリには存在しない技。**
`DASH_AUTO_TICKS` に行が無いのは欠落ではなく、**`fc`/`bc` は測る対象が
無い**ということ。引き継ぎ資料の元ビルドに行が無かったのも同じ理由と思われる。

`hud.lua` が別方向から同じ結論に達している - ダッシュ攻撃キャンセルの
トレーナーから**ザベルとデミトリを除外**している。ザベル側の理由は
「ダッシュが攻撃フラグを立てるので差が常に 0」とコメントにあるが、
デミトリは理由が書かれていなかった。**中断不可がその理由。**

`f`/`b`(平ダッシュからボタン)は単に未実測。足すこと自体は問題ない。

### 8.46 パッド経由の遅れた押しが二重になる (v222、未解決)

モリガンのダッシュ攻撃が 13 で**出たり出なかったり**した。入力履歴を見ると
**出たときは P が 2 回、出ないときは 1 回**。

`joypad.set()` は注入と同じエントリを**1 ティック遅れで**届け続けている。
通常はこれで「押した -> 押しっぱなし」と読まれ、エッジは注入側に立つ
(§3 参照)。ところが**押しが 1 ティックだけの場合**、注入分が離れてから
パッド分が来るので、**別々の押しエッジが 2 回立つ。**

```
13 で出た    13 に注入、14 にパッド分  -> 効いていたのは 14 のほう
13 で出ない  14 のパッド分が立たず     -> 13 の 1 発だけで不成立
14 にすると  14 に注入                 -> 1 発で安定
```

**つまり 13 は値ではなく、14 が偶然届いていただけ。**モリガンは 14 に修正。

**未解決。**この二重押しは:

* **チェーン可能な通常技を 2 回振る**恐れがある(v141/v154 で別経路の同種
  問題を潰した経緯があるので、同じ形)。
* 入力履歴に余計な 1 個を出すので、利用者が数えると合わない。
* **キャラ別の値を詰める作業を汚す。**「たまに出る」が能力ではなく echo で
  起きるので、境界を 1 ずらして観測してしまう。

塞ぐなら注入したティックとその次で `joypad.set` 側を抑える、あたりが筋。
**リリースには含めない**(挙動を変えるので実測が要る)。

### 8.47 前ダッシュにもタップの保証が要る (v225)

「デミトリのゼロデモンに対して最速ダッシュが出ない」。ガード後の前ダッシュ、
8 スパン中 4 つが失敗していた。**成功と失敗の差は 1 ティックだけ:**

```
        成功            失敗
free-2  lev=2 (前)      lev=1 (ガードの後ろを握ったまま)
free-1  lev=.           lev=.
free+0  lev=2           lev=2
free+1  $06=14 ダッシュ  $06=04 何も出ない
```

**失敗側は 1 回目のタップが存在しない。**前ダッシュはタップをフレーム側に
任せており、間に合わないことがある。**タップ 1 つはただの歩き。**

v210 で前ダッシュをタップ注入の対象から外したのは**半分しか合っていなかった。**
「前は握っていないので解放は要らない」は正しいが、**タップの到達保証は前にも
必要**だった。当時これで直ったように見えたのは、v213 以前はタップが署名
ティックに乗ることがあり(8.44)、そちらの害のほうが大きかったため。

v225: **タップは 4 種類すべてに保証**し、**解放はダミーが既に握っている
方向のときだけ**(`NEEDS_RELEASE` = 後ろダッシュと後ろダッシュ中断)。
前ダッシュで解放すると**ガードが 5 ティック外れるだけで得が無い。**

### 8.48 ブロックのアームは free-2 に立つこともある (v226)

v225 は悪化した(20 回中 2 回)。ログで理由が出た。

**最後のブロックアームから署名までが 1 ティック**しかない。7 スパン全部。

```
blk_arm -> press_defer = 1 ティック   x7
タップは _dstep = lead-5 = 5 か 6 で撃つ   ->  到達しない
```

`BLK_LEAD` は**アームから free まで 10〜11 ティック**を前提にしている
(§5.5)。デミトリのデモンをガードした場合、アームは **free-2** に立つ。
前提が成立していないので、そこから逆算する置き方は**どこにも当たらない。**

**アームの位置は free-2 から free-11 まで動き、事前には分からない。**

v226: **前ダッシュは狙うのをやめた。**アームでダッシュ方向を倒し、署名が
free-1 に中立を置くまで**そのまま保持する。**free がいつ来ても、その手前の
形は必ず「方向 → 中立 → 方向」になる。前方向はガード方向ではないので、
握り続けても後ろの解放が既に払っている以上のコストは無い。

**後ろは従来どおり狙う。**後ろは**解放を先に置く**必要があり、そちらは位置が
要る。実測で動いているので触らない。

**v226 は `return` していて全滅した (v227 で修正)。**

このブロックは**同じフックの中で、free-1 署名の処理より前**にある。v226 は
アームから毎ティック `return` していたので、**署名の窓がその中に入ると署名が
走らない。**アームが free-2 なら free-1 はまさにその中で、結果として
free-1 の中立も、2 回目のタップも、ボタンも出ない。**普通のガード後まで
出なくなった。**やられ後が無事だったのは、そちらがこの経路を通らないため。

**保持に早期 return は要らない。**後から走るものが最後に書いて勝つので、
署名ティックではそれが正しい動作になる。

**教訓: このフックの中で `return` するときは、その先に何があるか見ること。**
署名の処理は下にある。

### 8.49 硬直の本体は `$26`。強さは関係ない (v228) — **誤り。8.51 を見ること**

「ガード硬直を短くしている仕組み」を追った結果。

```
075E1A: move.b ($a,A6), D0          ; やられ種別
075E1E: lsl.w  #3, D0               ; 1 エントリ 8 バイト
075E20: move.w (A1,D0.w), ($54,A6)  ; +0 -> $54   A1 = 0x0764EA
075E2C: move.b ($5,A1,D0.w), ($59,A6) ; +5 -> $59

027D2C: lea    ($28ca0,PC), A0      ; 表は $1a8 と $a で 3 つから選ぶ
027D36: lea    ($28be0,PC), A0
027D40: lea    ($28c40,PC), A0
027D46: move.b ($54,A6), D0
027D4A: move.b (A0,D0.w), ($26,A6)  ; $26 = 硬直ティック数

024CA4: subq.b #1, ($26,A6)         ; 毎ティック 1 減る
024CA8: bne    $24cc0               ; 0 が復帰
```

**`$54` と `$59` は同じ反応エントリの別フィールド**(+0 と +5)。
つまり**硬直の長さと技の強さは設計上independent。**

実測がそれを裏付ける。**同じ `$59 = 2`(強)で硬直が 22 / 24 / 34。**

```
$59=2  硬直 22, 24   アーム free-2   <- 出ない
$59=2  硬直 34       アーム free-11  <- 出る
```

**`BLK_WAIT` と `BLK_LEAD` を `$59` で引いているのが誤り。**強さで待ちを
決めているので、強攻撃なのに硬直が短い技(ゼロデモン)では待ち 8 を消化した
時点で残り 2 ティックしか無く、そこにアームが立つ。

**`$26` は違った(v229 で否定)。**実測でガード 13 / やられ 9 スパンとも、
硬直中ずっと `$26 = 0`。0x027D46 の経路は実在するが、**この復帰を支配して
いない。**仮説は棄却。

### 8.50 硬直の長さはアニメーションデータにある (v229) — **誤り。8.51 を見ること**

ブロックは 0x02393A でガード状態を作り、**0x027EC0 にアニメーション id を
渡して抜ける。**つまり**ガード硬直の長さ = ガードアニメの長さ**であって、
強さから推定するものではない。ゲーム自身の数え方はこう:

```
027EEC: move.l (A0), ($20,A6)   ; $20 持続、$21 フラグ
027F70: subq.b #1, ($20,A6)     ; 毎ティック
027F7A: move.b ($1,A0), D0      ; セルのフラグ
027F80: bmi    $27f8e           ; bit7 -> ($18,A0) へジャンプ
027F88: st     ($21,A6)         ; bit6 -> 最終セル、アニメ終了
027F96: lea    ($18,A0), A0     ; セルは 24 バイト
```

**free までの残りティック = `$20` + 以降のセルの持続の合計**(bit6 のセルまで)。
`$1c` が現在のセルを指しているので、そのまま辿れる。bit7(ジャンプ)に当たった
ら長さが確定しないので nil。

**インパクトフリーズ中はステッパが回らない**ので、これは残り「アニメ時間」で
あって実時間ではない。フリーズが明けた時点から正確になる。

v229 で `anl` としてトレースに追加。**free-1 署名までの距離と一致するかを
実測で確認してから**、`BLK_LEAD` / `BLK_WAIT` を捨てる。

**なお「硬直の頭で入力しておく」案は使えない。**大攻撃の長い硬直では、free に
着く前に受付が切れる(コマンド認識のステップタイムアウトは 14〜19 ティック、
ダッシュのタップも実測で 10 ティックまで)。**待ちがあるのはそのため。**

### 8.51 ガード硬直は押し戻しスクリプト。カウンタは存在しない (v235)

8.49 と 8.50 はどちらも外れ。`$26` はガード中ずっと 0 だし、ガードアニメは
free の7ティック以上前に終わっている。P2 の `$000`〜`$3FF` と P1 の
`$000`〜`$1FF` を毎ティック掃いても、free に向かって数える値は一つも無かった。

**無いものは見つからない。** 数えるカウンタは存在しない。

ガードのディスパッチャは 0x024A22。`$07` をサブステップとする語テーブルで飛ぶ:

```
024A22: move.b ($7,A6), D0        ; $07 = サブステップ
024A26: move.w ($6,PC,D0.w), D1   ; テーブル基点 0x024A2E
024A2A: jmp    ($2,PC,D1.w)       ; 飛び先 = 0x024A2E + D1
        0008 -> 024A36   $07=0   $07 を 2 に進めてそのまま落ちる
        000C -> 024A3A   $07=2   毎ティック bsr $27DE4。真なら $07=4 にして 024ADA へ
        00AC -> 024ADA   $07=4   $04..$07 に 0x02020400、$184/$170/$1AB をクリア
        00CE -> 024AFC   $07=6   $26 カウントダウン(プッシュブロック成立時だけ)
```

`$26` が硬直に見えたのは 8.49 で `$07=6` の枝だけを見ていたから。通常の
ガードはそこを通らない。

硬直を終わらせているのは 0x027DE4:

```
027DE4: clr.b  ($118,A6)
027DEA: move.b ($59,A6), D0     ; 攻撃側の食らいデータ(0x0764EA+5)が決める反応タイプ
027DF0: lea    ($285de,PC), A0  ; タイプ別スクリプトの語オフセット表(符号付き、自己相対)
027DF8: lea    (A0,D0.w), A0
027DFC: move.w ($164,A6), D0    ; カーソル
027E00: move.b (A0,D0.w), D0    ; 1ティック 1バイト
027E04: bmi    $27e2a           ; 負 = 終端 → 1 を返す → ガード終了
027E06: addq.w #1, ($164,A6)
027E22: add.w  D0, ($10,A6)     ; 負でなければ、そのティックの X 押し戻し量
```

**押し戻しの距離と硬直の長さは同一のデータ。**バイトが尽きたら硬直が明ける。

表は 0x0285DE。**データ領域なので `mame_code` のリスティングでは読めない**
(8.6.108 と同じ CPS2 の罠)。実機から読んだ実バイト:

|---|---|---|
| 0 (弱) | 11 | `04 04 04 04 03 03 03 02 01 01 01` |
| 1 (中) | 16 | `03 04 04 04 05 06 06 05 04 03 02 01 01 01 01 01` |
| 2 (強) | 20 | `04 05 06 07 08 08 08 07 06 05 04 03 02 01 01 01 01 01 01 01` |
| 3 | 24 | `0a` ×8 から `01` まで |
| 4 | 48 | 全部 `00`(押し戻し無し) |

近似していたことの答え合わせになっている。

#### なぜゼロデモンで最速ダッシュが出なかったか

**`$158` とスクリプトは別の時計で走っている。** `$158` は接触時に 14 が入り
0x022492 が毎ティック減らす。`$164` は**キャラが実際に動いたティックしか
進まない**ので、ヒットストップ中は止まる。デミトリのゼロデモンは `$164` を
**12ティック 0 のまま**保持する。その間に `$158` は 14→2 まで燃えてしまう。

`reversal_logs_archive` の完全なブロック 710 本を再生した結果:

| スクリプト長 | 旧(`$158` ゼロ立ち上がり + 待ち) | 新(残り = 長さ − `$164`) |
|---|---|---|
| 20 (強) | lead −1 / 0 / アーム無し が **229本中111本(48%)** | **221本が lead 10〜11** |
| 16 (中) | 8〜10 に 97/132 | 126/132 が 10〜11 |
| 11 (弱) | 7〜9 に 321/349 | 335/349 が 9〜10 |

**ガード硬直が短かったのではない。**ガードされたゼロデモンは 20 ティックで
普通の強と同じ。壊れていたのは起点のほうだった。

新方式は残りティックを直接引く。閾値は `min(BLK_ARM_LEAD, 長さ−1)`。
スクリプトが読めない反応タイプに当たったときだけ旧経路に落ちる。

#### ゼロデモンとノーマルデモンの違いはヒットストップの長さ

**ガード硬直そのものは同じ 20 ティックで、両者に差は無い。**違うのは
ガードした瞬間の止まり(`$06 = 0x00`)の長さ:

| | ノーマルデモン | ゼロデモン |
|---|---|---|
| ヒットストップ | 約 12 ティック | 約 2 ティック |
| ガード硬直 | 20 | 20 |

`$158` は止まっている間も減り続け、`$164` は止まる。**両者はヒットストップ
の長さちょうどぶんだけズレる。**

```
ノーマルデモン   $158  14 …  3 | 2  1  0     $158=0 でカーソル 3  残り17  旧アーム = free-9  ○
                 $164   0 …  0 | 1  2  3

ゼロデモン       $158  14 13 | 12 … 1  0     $158=0 でカーソル13  残り 7  旧アーム = free 以降  ×
                 $164   0  0 |  1 … 12 13
```

アーカイブ実測:

| ヒットストップ | 本数 | 旧ルールの結果 |
|---|---|---|
| 12 ティック | 110 | **89 本が lead 8〜10(良好)** |
| 2 ティック | 163 | **90 本が free 以降 または アーム無し(死)** |

「ゼロデモンの硬直が短い」のではない。**止まりが短いぶん、見ていた時計だけが
先に進んでいた。**

#### アームの時刻は「いつ狙うか」ではない。技が出るか出ないかを決める (v237)

**ここで二回失敗した。**残りが正確に取れたので、v235 は素直に lead を 11 に
した。通常のガードの精度が落ちた。タップの位置がずれたせいだと考えて v236
でタップを free からの距離で置き直した。**タップは狙いどおり free−3 にゼロ
ずれで乗っていた**(25/36/53 件)のに、精度は戻らなかった。

アームは**スケジュールの基準点ではない**。アームで `make_input_sequence` が
走るので、**アームを動かすとシーケンスの最終入力の位置ごと動く**。それが
free+0 から外れれば、8章冒頭の規則どおり「遅い」ではなく**出ない**。

旧 `$158` 基準の実測 lead は通常のガードで 8〜9(弱 349 本の最頻が 8、
中 132 本が 9)。`BLK_ARM_LEAD = 9` にすると、カーソル基準でも同じ 8〜9 に
入る。アーカイブ全体を再生した比較:

| 区分 | 旧 `$158` 基準 | 新 閾値9 |
|---|---|---|
| 長さ20・壊れていた群 | lead 7〜10 が **5%** (7/130) | **96%** (125/130) |
| 長さ20・その他 | 91% | 100% |
| 長さ16 | 71% / 90% | 100% / 98% |
| 長さ11 | 71% / 94% | 75% / 100% |

どの区分でも旧以上で、通常のガードは同じ帯のまま。**通常を動かさずに、旧
ルールが free を追い越していた回だけを直す**という要求どおりの形になった。

#### タップの位置は free からの距離で置く (v236)

`_dstep`(アームからの相対) × 推定 lead は見積もりを二段重ねにしていた。
アームはフレームフックが置くので4ティック幅でばらつき、latch した lead も
それを引き継ぐ。スクリプトの残りは毎ティック正確なので、そちらで置く。

アーカイブ全体で tap1 の位置と成功率:

| tap1 位置 | 長さ11 | 長さ16 | 長さ20 |
|---|---|---|---|
| free−1 | **0%** | **0%** | 20% |
| free−2 | 100% | 100% | 83% |
| **free−3** | **100%** | **100%** | **100%** |
| free−4 | 85% | 100% | 94% |
| free−6 | 100% | **33%** | **38%** |

`BACK_TAP_BIAS` は本来の意味に戻した ＝ **tap1 を free の何ティック前に置くか**
(3)。窓は `BACK_TAP_HOLD_TICKS` 分で free−3 と free−2、解放はその手前の
`BACK_TAP_NEUTRAL_TICKS` 分。やられ側の経路にはスクリプトが無いので
`_dstep` のまま。

### 8.52 影縫い(近接ガード)はゲーム自身が持っている (v239-v245)

ユーザの言う「影縫い」＝後ろを入れたときにガードポーズを取って動けなくなる
状態。仕様はこう:

* **飛び道具は画面上のどこにいても効く**(距離を見ない)
* **通常技・必殺技は技ごとに影縫い距離が決まっていて、その外では後ろを
  入れても歩くだけ**
* 通常技は持続が短いので外で下がり始めても歩きが見えない。**デモンクレイドル
  は持続が長いので徒歩が出る**

ゲームのルーチンは 0x02766A / 0x027688、返り値 D0 = 1 で成立。二段構え:

```
0276A6: moveq #$1f, D6 / lea ($1400,A5), A4     ; A5=0xFF8000 -> 0xFF9400
0276AC: cmpi.b #1,(A4)     / bne 次              ; 生きているか
0276B2: tst.b ($1,A4)      / beq 次
0276B8: tst.b ($a2,A4)     / bne 次
0276C0: move.b ($70,A6),D0 / cmp.b ($70,A4),D0 / beq 次   ; 自分の持ち物なら飛ばす
0276CA: movea.l ($1c,A4),A1 / tst.b ($17,A1) / bpl 成立    ; 攻撃セルなら距離を見ずに成立
0276D6: lea ($100,A4),A4   / dbra D6            ; 32個
        ^ 前半。飛び道具・影縫いはここ。距離判定が無いのが仕様と一致する

0276E2: tst.b ($154,A4) / bne 成立               ; 唯一の無条件
0276EA: tst.b ($105,A4) / beq 不成立
0276F8: tst.b ($ac,A4)  / bne $27706            ; $38 による却下を飛ばすだけ
027712: movea.l ($8c,A4),A1                     ; 技ごとの判定枠テーブル
027716: move.b ($a,A0),D0 / lsl.w #5            ; セルの枠 index * 32
027724: move.w (A1),D0    / 向きで符号反転
02772E: add.w ($10,A4),D0 / sub.w ($10,A6),D0   ; 枠の X と自分の X の距離
02773A: move.w ($4,A1),D1 / addi.w #$80,D1
027742: cmp.w D1,D0 / bhi 次のセル / 成立
027754: lea ($18,A0),A0                         ; 残りのセルを先読みする
02775A: 最後に素の |dx| < 0x100 の保険
```

#### 直したもの

`autoguard.lua` の `dummy_guard()` が持っていた判定は
`attack_flag ($105) and |dx| < 0x100` で、これは**最後の保険 0x02775A だけを
抜き出した形**だった。前半のオブジェクト走査が無いので影縫いを見ず、技ごとの
枠データを見ないので空振りでも後ろを入れていた。両方を移植した。

#### `$4AC` は「無条件にガード」ではない (v245)

移植しても症状が消えなかった。専用ログ(`reversal_logs/ag_prox.json`)を取ると、
**後ろを押した17件が全部** `$4AC` の早期リターン経由で、`dx` 302 から 33 まで
**距離に関係なく**押していた。移植した判定には一度も到達していなかった。

ゲームの `$ac` は 0x0276F8 で `bne $27706`、つまり `$38` による却下を飛ばして
**範囲判定の途中に入る**だけ。成立を確定させるものではない。無条件なのは
`$154` (0x0276E2) だけ。`$149` はルーチンに存在しない(飛び道具は前半の
オブジェクト走査が受け持つ)。早期リターンは判定が読めなかったときの保険に
降格した。

#### タップではなくホールド。ティック化はしてはいけない (v246 → v247)

後ろ入力は元々1表示フレームのタップだった。ターボ3では約1.6ティックで、
フレームコールバックは4割のティックを取りこぼす — 直すべき欠陥に見えたので
v246 でティックフックに移し、立ち上がりから3ティック保持にした。

**飛び道具が必ず当たるようになった。**飛び道具はもともと `$149` の早期
リターンが「画面にある間ずっと後ろを入れる」形で守っており、それを v245 で
保険に降格したうえ v246 でタップにしたので、飛び道具が届く頃には手を
離していた。

さらに**タップにしていた理由自体が、近接判定の移植で消えていた。**
間合いの中か分からないから一瞬だけ押していたのであって、`prox` が真＝
ゲームがガードポーズを認める＝**後ろを入れても歩かない**。真の間はずっと
押してよい。

押しに要るのはティック精度ではなく、**飛んでくるものが到着したときにまだ
押していること**だった。ここは表示フレームで足りる。ティックが要るのは
「free+0 に乗せる」類の話であって、この機能はそれではない。

### 8.53 PB カウントは「押した回数」。成立回数ではない (v248-v250)

ユーザの指摘: 「画面で 6 を一度も見ていない」「6 回押せば 100% 出るのだから、
文字通り 6 回押せるようにするための数字のはず」。どちらも正しかった。

#### 表示していたものが違った

`$170` は**成立した瞬間に止まる**(8.27。`$184` の判定 0x0275E0 が押しの判定
0x0275FE より手前にある)。だから訓練の指標にならない。保存ログを再生すると:

| `$170`(旧表示) | 実際に押した回数 | 本数 |
|---|---|---|
| 3 | **6** | 22 |
| 4 | **6** | 28 |
| 5 | **6** | 30 |
| 6 | 6 | 40 |

**132 本中 120 本が実際には 6 回押していた。**ツールは正しく 6 回押していて、
表示だけが成立回数を出していた。さらに HUD は「6 以上なら緑」にしていたので、
**成立 90 本のうち 81 本(90%)が成立しているのに緑にならなかった。**

#### 読む時刻も間違っていた

`$170` を表示フレームごとに読み、窓 `$1AB` が 0 になった立ち上がりで確定して
いた。ガード終了処理は `$184`/`$170`/`$1AB` を同時にクリアする(8.51)ので:

* **中・強** — 窓は 14 ティック、硬直は 16/20。猶予は数ティックしかなく、
  フレームコールバックが 4 割のティックを落とすので跨ぐと 0 を掴む
* **弱** — 硬直 11 < 窓 14。`$1AB` は自然に 0 にならず、存在する 0 は
  クリアが書いたものだけ。**必ず 0 になる**

実測でも中攻撃のガード 5 本すべてが末尾 `(1,0) → (0,0)`。

#### 直し方

数え上げを 0x0275E0 で自前で行う。**窓の判定はゲームのまま** — そこに到達した
時点で 0x0275D8 が `$1ab != 0` を保証しているので、こちらが期間を広げる余地は
無い。`$184` の早期脱出だけを再現しないので、成立後の押しも同じく数える。
新しい窓 (0x023966 の `move.b #$e,($1ab,A6)`) で 0 に戻す。

成立表示は 0x027632 (`move.b #$1,($184,A6)`) をフックして緑にする。

### 8.54 ステージ座標と位置設定 (v254-v273)

`$10` は世界座標の X(16.16 の上位語)。**外から書いた位置はゲームに補正されない** —
壁を越えて書けばキャラはステージ外へ出て画面から消える。

#### キャラはカメラの枠に閉じ込められている

キャラ単独ではステージ端に届かない。ゲームが2人を画面内に保つので、
片方が右にいると相手はそれ以上左へ行けない。壁を測るには**2人とも同じ隅へ
追い込む**必要がある。実測(2ステージ):

| | 左壁 | 右壁 | 幅 |
|---|---|---|---|
| ステージ A | 280 | 1000 | 720 |
| ステージ B | 277 | 1000 | 723 |

**全ステージ同じ広さ。**ステージ別テーブルも範囲変数の特定も要らなかった。

#### 開幕位置

ラウンド開始時にゲーム自身が置く位置。`554 / 728`、間隔 **174**、中点 **641**。
壁から出る中央 640 と一致する(独立した2つの測定が揃った)。

捕捉は「どちらかの `$10` が 0 に触れたら武装 → 2人とも非0 かつ **8フレーム
静止**」。条件が緩いと配置途中を拾い、426/728(間隔302)のような偽物が採れる。
それは画面の8割を占める間隔で、開幕ではない。キャラによって変わり得るので
毎ラウンド採り直す。

#### 動かし方

**滑らせる。テレポートしない。**一気に飛ばすとカメラが追いつけず、キャラは
画面端まで引き戻される。毎フレーム 12px ずつ動かせば歩いているのと同じ状況
になり、カメラは自分で追いつく。毎フレーム位置を読み直すので、ゲームが
拒んだ移動は反映されず、カメラが追える速度に自動的に収まる。

スクロール語(`0xFFB810`/`890`/`910`/`990` の 0x80 刻み4つ)を直接書いても
少ししか動かない。ゲームがキャラの実位置から計算し直すので、**出力であって
操作点ではない。**

#### 並びの入れ替え

キャラは相手を通り抜けられない。**位置を交換する。**ただし**滑走の前に**やる
こと。後にすると壁際で重なったまま残り、押し離しが外側を壁に押し込み、壁が
押し返して膠着する(プルプルの正体)。先にやれば直後の滑走が重なりを解消する。
交換の前に内側を 24 だけ壁から離しておく。

#### 入力の衝突

メニューの設定変更はレバーを倒す操作で、**その入力がそのままキャラを歩かせる。**
設定が変わった瞬間に動き出すと、滑走の間ずっとプレイヤー自身の入力と喧嘩し、
交換は歩きで戻される。設定が 20 フレーム変化しなくなってから動き出す。

### 8.56 プッシュブロックをガードの種類にする (v285-v290)

「プッシュブロック後にダッシュ攻撃の反撃が確定するか」を調べたい。
`Guard Action Type` に居るとカウンターと排他なので成立しない。**防御の側**
(`Guard`)へ移し、強さも項目に畳んだ:
`Push Block (All Light / All Medium / All Heavy)`。

#### 関門が4段あった

出るまでに4回外した。`guardCancelCheck` はガードアクション用に作られており、
プッシュブロックはそのどれにも該当しない:

1. 先頭の `shouldGC()` — Guard Action Frequency の抽選。Type が None だと 0%
2. `guard_action == 'none'` の early return
3. `gc_freq == 0` の early return
4. 連鎖末尾の `else return {}`

**どれもガードアクションであることを前提にした関門**なので、`Guard` 側から
来た押しには一つも適用してはいけない。

#### counter.sequence に置いてはいけない

計測(一時プローブ)で確定した: ガードエッジ16回、シーケンス生成16回、
**積み込み0回**。`counter.sequence` はガードアクションの枠で、その後に
カウンターの分岐が `should_counter == false` のあいだ `nil` で上書きする。
ブロック中はずっと false なので、作っては捨てるを繰り返していた。
生成したその場で `queue_input_sequence` する。

#### 成立すると時計が変わる

これが「プッシュブロックは出るが最速行動が出ない」の原因。

```
024A6C: move.b #$6, ($7,A6)      ; 成立で $07 = 6 へ
024A72: move.b #$a, ($26,A6)     ; $26 = 10
024AFC: subq.b #1, ($26,A6)
024B00: bne    $24b22
024B02: move.l #$2020400, ($4,A6)  ; 通常ガードと同じ free 署名
```

**ガードスクリプトは捨てられる**ので `長さ − $164`(8.51)は意味を失い、
アームが永久に発火しない。`$07 == 6` のときは **`$26` がそのまま残り
ティック数**なので、それを使う。10 から始まるので lead 9 で掛かり、通常
ガードと同じ最速になる。

#### 成立したら連打を止める

`$184` が立つと 0x0275E0 が以降の押しを無視するので、残りの連打は無意味。
しかも**配送枠を占有し続ける**ため、後続のカウンターが積めない。捨てる。

### 8.9 撤去した機能

**True Reversal**(v166 で撤去)。ゲームのリバーサル窓を見る 2 通りの判定を
切り替えるオプションだった。存在した理由はツールチップ自身が書いている —
「ターボ速度では真の 1 フレームリバーサルは 75% しか成立しない。FBNeo の Lua の
粒度が足りないため、他のリバーサル動作は最速より 1〜2 フレーム遅い」。
**`joypad.set` でフレーム 1 を取れなかったことへの対処**である。

現在はどのリバーサルもティックフックが `$1a7` / `$158` /
`ticks_to_landing()` / free−1 シグネチャで置いており、**この窓を見ていない。**
残っていた `should_reversal` はリアクティブなフォールバックと後始末を
gate するだけで、切り替えても利用者に見える違いは無く、誤解を招くだけだった。
既定が選んでいた側(`bulletproof_reversal`)に一本化した。

**多段カウンター**(`guard_action_hit`、v148〜v149)も撤去済み(§5.5.4)。

## 9. 未解決・既知のリスク

1. **移動起き上がりの `$a` 分岐。** 汎用ハンドラは転がり後のアニメを
   `$a` の符号で 0x46 / 0x48 に分ける。両者の長さが違えば同じ `$07`=4 でも
   終端値が割れる。実測ではモリガン 47(94 スパン)、ビシャモン 30(270 スパン)
   とも単一値で実害なし。割れれば `kd_report.py` の `end $1a7` に二峰性として出る。
   **Q-Bee ではこれが実際に起きており**、彼女だけ `$a` の符号を鍵にしている(§4.7)。
2. **未実測のキャラ ID が 3 つある。**
   * **0x0B**(Zabel の 2 つ目の枠)はアニメスクリプト表が 0x04 と同一なので
     0x04 の値を流用している。
   * **0x12 Dark Gallon** は `vsavscriptv2.lua` 自身が「ガロンと全く同じ」と
     書いているので Gallon の値を流用している。
   * **0x18 Oboro** は表に入れていない。ビシャモンの別版だが同一とは限らず、
     根拠が無い。`$21` 規則へフォールバックする。
3. **`$1c` からの残りアニメ時間**を直接使えば表そのものが不要になる。
   トレースに `$1c` を追加済みで、次のバッチでオフライン検証できる。
4. **ガード硬直後のリバーサル**は未着手。
5. **run-ahead。**(2026-08-22 に整理。着手はしていない)

   * **検出はできている。** `0xFF8081` が後退したときだけ数える(前進のジャンプは
     ラウンド遷移やメニューでも起きるので数えない)。実測で ON なら
     ティック対の 24.4%、OFF なら 0。
   * **Lua から設定は読めも書けもしない。** FBNeo の luaengine.cpp が公開して
     いるのは `fba.speedmode` 程度で、設定にアクセスする関数は無い。
     `nRunAhead` / `bRunAhead` / `bBurnRunAheadFrame` はどれも Lua に出ていない。
     よって「トレモ中だけ Lua で切る」は不可能。
   * **burn.cpp に `bBurnRunAheadFrame` は実在する。**コメントは
     「for drivers, hiscore, etc, to recognize that this is the 'runahead frame'」。
     欲しい旗そのものだが C++ 側にしか無い。実行順(実フレームが先か投機が先か)は
     burn.cpp ではなく run.cpp 側で、Fightcade は fork なので上流と同じ保証も無い。
   * **難所は savestate ではない。**エミュレータのメモリは復元されるが Lua の
     変数は復元されないので、アームやシーケンス進行が投機実行のぶんまで進む。
     さらに投機パスで書いた入力は破棄される — free+0 に置く仕組みなので致命的。
   * **手が届く形。**自前の状態を**エミュレータの RAM に置く**。FBNeo 自身の
     save/restore が巻き戻してくれるので `savestate.registerload` も実行順の
     知識も要らず、**順序に依存しない。**オフライン専用なので未使用 RAM への
     書き込みは許される。
   * **未使用候補は洗い出し済み。**4 枚の 64KB ダンプ(2 ステージ x 左右端)で
     常に 0 の連続領域が 147 箇所 48.6KB。最大は `0xFF619A`(7666)、
     `0xFF4898`(5371)、`0xFF1E7A`(4146)。ただし「4 枚で 0」は未使用の証明では
     ないので、`memory.registerwrite` を張って長時間ゲームが書かないことを
     確かめる工程が要る。
   * **利用者にとっての本当の問題**は「トレモ用に切って対戦で戻し忘れる」こと。
     つまり run-ahead 対応の価値は機能ではなく**設定を触らせないこと**にある。
6. **0x0221C8 と 0x02A55A** の値はまだ listing 読みに依存している。
   v133 で DUMP するようにしたので次のバッチで確定する。

## 10. 過去に誤っていたこと(再発防止)

同じ穴に落ちないための一覧。**どれも実際に時間を失った。**

| 誤り | 正しくは |
|---|---|
| 起き上がりハンドラ表 0x0BD47A でコマンドの範囲を区切った | **コマンドは 0x0BD3FA。**別キャラの技を読んでいた |
| `jmp ($2,PC,D1.w)` の飛び先を PC+D1 とした | **EA = PC + 2 + D1** |
| listing のデータテーブルをそのまま信じた | **CPS2 はオペコード空間のみ復号。データは DUMP で採る** |
| `$21 == 0x40` を arm の起点にした | **終端セルの長さがキャラごとに違う。**`$1a7` の終端値を使う |
| `$1a7` の終端値が ROM のスカラ表にあると考えた | **無い。**アニメのセル長合計から出る(§5.4) |
| コマンド認識が `$122` を読むと考えた | **`$12a`。**向き反転の条件も別(§2.1) |
| 入力ステージ2の入口を 0x014E7A と書いた | **`jsr $14e8a`** |
| レバーを OR で立てた | **代入する。**マッチャは完全一致なので、残った「下」と新しい「後」が斜めになり弾かれていた |
| HCF/HCB を対称な 5 歩とした | **4 歩、非対称** |
| コマンドの最初の方向を省いた | **最初の方向もコマンドの一部** |
| 360 を 6 点(斜め込み)で入れた | **4 方向。**回転マッチャは `cmpi` なので斜めは弾かれる |
| 回転は「歩数が 0 になれば成立」と考えた | **その後さらに 1 方向必要。**合計 4 方向 |
| リバーサル判定の窓を 20 ティックにした | **`delay == 0` が本来の定義。**12〜13 ティック遅れを成功に数えていた |
| 移動起き上がりの分類を `$1a7 > 40` で行った | **モリガンの数値。**開始時の `$07` で分ける |
| run-ahead を有効にしたまま調整した | v81〜v86 のデータは全て無効。**必ず無効を確認する** |
| `(delay or 99)` で判定した | Python の falsy-zero。**`is not None` で書く** |
| フレーム側のコードで特定ティックを狙った | **フレームは 4 割のティックを見ない**(§0) |
| `KD_ARM_AT = 23` を全キャラ共通の閾値として使った | ザベル(終端 22)とサスカッチ(23)は起き上がり全区間がこの内側に入り、空中復帰用のフラッシュに pre-buffer を食われていた |
| 着地系と `$1a7` 系の両方に同じ起き上がりを arm させた | ビクターが 1 ダウンで 360 を 2 回入れていた。**テーブルに値があれば `$1a7` 系が専有する** |
| ティック系に `grounded` 条件を残した | `$21` を見ていた頃の名残。`$1a7` は空中でも進む。**残すとビシャモンの移動起き上がりが arm できない** |
| 旧経路の `inject_mask` を残したまま新経路で押した | **必殺技では重なって見えないが、通常技は連打キャンセルで 2 回振る**(§8.5) |
| ディレイを先頭の空エントリで表現した | ティック駆動では**モーションが前にずれるだけ**で効かない。押す位置のオフセットとして当てる(§8.5) |
| ボタンの無いエントリでも方向を先入れした | **ダッシュはエッジが立たない。**先入れは後ろにボタンが続くときだけ(§8.5) |
| `SEQ_LEN` を「必殺技コマンドの一覧」として使った | **エントリ数の表**で素の方向もダッシュも載っている。必殺技判定には明示リストを使う(§8.5) |
| 単発エントリのシーケンスはホールド不要だと考えた | **保持しないとティック経路に入らない。**素の通常技が全部これ(§8.5) |
| 入力履歴はフレームに 1 回読めば足りると考えた | **1 ティックのエントリはサンプルの隙間に落ちる**(§8.2) |
| 画面下部の入力履歴がダミーのものだと思い込んでいた | **下部は P1(人間)。**ダミーは**右上の縦列**で、別ファイル(`vsavscriptv2.lua`)の別実装(§8.2) |
| ダミーの表示が `joypad.getdown` を読んでいることに気付かなかった | v131 以降ツールは `joypad.set` を使わない。**パッドには何も映らない**(§8.2) |
| 前方参照の `local` を代入より後で宣言した | 代入はグローバルに書かれ、後の `local ... = nil` がそれを覆い隠す。読み出し側は永久に nil。**Character Specific が全く出なくなった原因**(v164) |
| `check_lua_scope.py` の出力を読まなかった | **検出されていたのに見落とした。**件数だけ見て中身を読まないなら走らせる意味が無い |
| ヘルパを使う場所より下で `local` 宣言した | Lua は未宣言名をグローバル読みにするので `luac -p` は通る。**`check_lua_scope.py` を必ず走らせる**(4 回やった) |
